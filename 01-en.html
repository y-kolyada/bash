    Key components of Bash

    The six mechanisms every script is built from. Knowing the order they run in is what separates an engineer who fixes a script in a minute from one who edits it by guess.

    The key idea of this page #

    Bash is not a language of commands but a pipeline that processes one line of text, and nearly all of its “oddities” follow from the order of that processing. The shell first splits the line into tokens, then performs expansions in a strictly defined sequence, cuts the result into words, expands filename patterns, and only then starts processes. That is why a path with a space breaks a command, why quotes change meaning, and why a failure in the middle of a pipeline disappears. The six sections below are the six places where scripts actually break. Assessments ask about exactly these, because the answer shows whether you understand the mechanism or merely remember a recipe.

    1 · Parsing the command line #

    The shell reads the line, splits it into tokens on operators (|, ;, &&, >), and only then starts expanding. The order is fixed, and it is the single most asked question:

    1. brace expansion    {a,b}
2. tilde              ~
3. parameters         $var ${var}
4. command subst.     $(cmd)
5. arithmetic         $((1+2))
6. word splitting     on IFS
7. filename globbing  *.txt
8. quote removal

    Two consequences. Globbing runs after parameter expansion, so f="*.txt"; echo $f prints a file list while echo "$f" prints the asterisk. And the reverse: {1..3} expands before parameters, which is why {1..$n} does not work.

    Typical question: “in what order does Bash perform expansions, and why does the result of echo $f depend on quoting?”

    2 · Expansion and word splitting #

    After substitution Bash cuts the result into words on the characters in IFS — by default space, tab and newline. Quotes suppress that split, and that is their only real job.

    f="My File.txt"
rm $f     # two targets: My and File.txt
rm "$f"   # one target, correct

    The same difference applies to argument lists: "$@" expands to separate arguments with their boundaries intact, while $@ and "$*" do not. The rule is simple: an unquoted expansion must be a deliberate decision, never a default.

    Typical question: “how do "$@", $@ and "$*" differ, and what breaks on paths with spaces?”

    3 · Processes and redirection #

    A process has three open descriptors: 0 input, 1 output, 2 errors. Redirections are applied left to right, and the order changes the result:

    cmd >log 2>&1   # both streams to the file
cmd 2>&1 >log   # errors stay on the terminal

    In the second case 2 copies the current destination of 1 — the terminal — and only afterwards does 1 move to the file. The same area covers <<EOF (here-document), <<< (here-string) and exec 3>file for long-lived descriptors.

    Typical question: “why do 2>&1 >log and >log 2>&1 produce different results?”

    4 · Pipelines and exit codes #

    Pipeline stages start simultaneously, each in its own process. By default the pipeline's exit code is the last stage's, so a failure in the first stage is lost silently:

    false | tee out
echo $?                  # 0
echo "${PIPESTATUS[@]}"  # 1 0
set -o pipefail
false | tee out
echo $?                  # 1

    This also explains why set -e does not save you: it reacts to a command's code, and here the command is the whole pipeline. And why a variable changed in a loop after | is empty afterwards: the loop ran in a subshell.

    Typical question: “how do you get the exit code of one specific pipeline stage, and why does set -e not fire here?”

    5 · Variables and scope #

    A shell variable is visible only to the shell itself; export marks it for handing down to child processes. A subshell inherits values but never returns its changes — braces, unlike parentheses, do not create a subshell:

    x=1; ( x=2 ); echo $x   # 1
x=1; { x=2; }; echo $x  # 2

    Inside a function a variable is global by default — local is mandatory, or the function silently overwrites someone else's value. Safe defaults: ${var:-fallback} instead of an empty string, and set -u so that a typo in a name stops the script rather than continuing with nothing.

    Typical question: “how does export differ from a plain assignment, and why is a function without local dangerous?”

    6 · Signals and traps #

    A signal is an asynchronous message to a process. trap installs a handler, and the only reliable way to clean up after yourself is a trap on EXIT: it fires on every termination, including errors and interrupts:

    tmp=$(mktemp)
trap 'rm -f "$tmp"' EXIT
trap 'echo interrupted; exit 130' INT

    A script killed by signal N exits with 128+N: 130 for Ctrl+C (SIGINT), 143 for SIGTERM. SIGKILL (9) can never be caught — so “reliable cleanup on kill -9” does not exist, and that is a deliberate property of the system rather than a gap in it.

    Typical question: “how do you guarantee a temporary file is removed on any termination, and why can SIGKILL not be trapped?”
