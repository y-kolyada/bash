    Слабости и границы

    Честный список того, что в Bash устроено плохо, и признаки, по которым видно: задача уже не его. Без этого раздела предыдущий был бы рекламой.

    Главная мысль страницы #

    У Bash четыре слабости, которые нельзя обойти мастерством: дырявая обработка ошибок, отсутствие структур данных, целочисленная арифметика и параллелизм без синхронизации. К ним добавляются две приобретённые: читаемость, падающая после трёхсот строк, и переносимость, которая ломается сразу по двум независимым причинам - другая оболочка и другие утилиты. Ни одна из них не делает язык плохим: они очерчивают область, в которой он лучший. Опасность не в слабостях, а в том, чтобы не заметить, как задача из этой области вышла. Последний раздел страницы - список признаков, по которым это видно заранее.

    1 · Обработка ошибок: set -e дырявый #

    Главная слабость, и она же самая опасная, потому что выглядит как решённая проблема. set -e создаёт ощущение защиты, а дыр в нём больше, чем помнит наизусть любой инженер.

    set -e

f() { false; echo "выполнится"; }
if f; then :; fi   # -e отключён

a=$(false)         # поймает
echo $(false)      # не поймает

false || true      # намеренно молча

    Правило: внутри условия, слева от && и ||, в теле функции, вызванной из условия, - set -e не действует. Добавьте сюда отсутствие исключений, отсутствие стека вызовов при падении и невозможность поймать ошибку и продолжить с восстановлением - и получите язык, в котором надёжная обработка ошибок требует дисциплины, а не поддержки языка.

    Что спрашивают: «В каких случаях set -e не срабатывает и как это обходят?»

    2 · Данных нет, есть текст #

    В Bash один настоящий тип - строка. Массивы есть, но они не передаются в функции, не вкладываются друг в друга и не возвращаются наружу. Структур нет вовсе.

    # это не массив массивов,
# это строка с пробелами
arr=("a b" "c")
other=("${arr[@]}")   # копия - так

f() { local -n ref=$1; }  # bash 4.3+
# передать массив иначе нельзя

cat data.json | jq -r '.items[].id'
# JSON в bash - всегда через jq

    Любая работа с JSON, YAML или CSV - это внешняя программа: jq, yq, awk. Пока данных мало, это нормально. Как только появляется вложенность, соединение двух источников или изменение структуры - вы пишете программу на jq внутри программы на bash, и читать это будет некому.

    Что спрашивают: «Как в Bash передать массив в функцию и почему это неудобно?»

    3 · Арифметика только целочисленная #

    Встроенная арифметика Bash не знает дробей. Совсем.

    echo $(( 7 / 2 ))        # 3
echo $(( 10 * 95 / 100 )) # 9

echo 'scale=2; 7/2' | bc  # 3.50
awk 'BEGIN{print 7/2}'    # 3.5

    Любой процент, среднее, время в секундах с долями - это вызов bc или awk, то есть внешний процесс на каждое вычисление. Если в задаче есть математика, Bash - неправильный инструмент, и это не вопрос мастерства.

    Что спрашивают: «Как в Bash посчитать среднее или процент и почему это неудобно?»

    4 · Параллелизм без синхронизации #

    Запустить сто задач одновременно просто. Сделать это правильно - нет: в языке нет ни мьютексов, ни очередей, ни безопасной записи в общее состояние.

    for f in *.log; do
  process "$f" &
done
wait            # код возврата - не ваш

# ограничить и поймать отказ:
printf '%s\0' *.log \
  | xargs -0 -P4 -n1 process

    Два фоновых процесса, пишущих в один файл, перемешают строки. Счётчик, увеличенный в сабшелле, снаружи не изменится. Код возврата wait без аргументов ничего не скажет о том, кто упал. xargs -P и parallel закрывают простые случаи; всё, что сложнее «обработать N независимых файлов», - повод уйти из Bash.

    Что спрашивают: «Как ограничить число параллельных задач в shell и как узнать, что одна из них упала?»

    5 · Читаемость падает после трёхсот строк #

    Синтаксис Bash оптимизирован под набор в одну строку, а не под чтение через полгода. Цитирование, подстановки и проверки складываются в текст, который трудно просматривать глазами.

    [[ -n "${v:-}" ]] && [[ "${v}" != "x" ]] \
  || { echo "нет"; exit 1; }

# условие, действие и обработка
# ошибки - в одной строке

    Добавьте отсутствие пространств имён, глобальные переменные по умолчанию и то, что ошибку в имени переменной ловит только set -u. Практический порог - около трёхсот строк: дальше скрипт начинает требовать от читателя тех же знаний, что и от автора, а это ровно то, чего избегает поддерживаемый код.

    Что спрашивают: «Где граница, после которой скрипт пора переписывать на другом языке?»

    6 · Переносимость: два разных мира #

    «Работает на моей машине» в shell имеет две независимые причины: не та оболочка и не те утилиты.

    #!/bin/sh
echo ${arr[0]}   # в dash - ошибка

sed -i 's/a/b/' f   # GNU
sed -i '' 's/a/b/' f # BSD/macOS

stat -c %s f     # GNU; BSD: -f %z
date -d @0       # GNU; BSD: -r 0

    /bin/sh в Debian и Ubuntu - это dash, а не Bash: массивов, [[ ]], подстановки процессов и замены по шаблону ${v//a/b} там нет. (local, вопреки распространённому мнению, в dash есть.) В Alpine внутри контейнера оболочка - ash из busybox, и половина привычных ключей утилит работает иначе. В macOS Bash версии 3.2, а утилиты - BSD.

    Решение честное и скучное: либо явный #!/usr/bin/env bash и отказ от POSIX-совместимости, либо проверка через shellcheck -s sh и отказ от удобств. Середины нет, и выбирать надо осознанно.

    Что спрашивают: «Чем sh отличается от bash и почему скрипт ломается в Alpine или на macOS?»

    7 · Когда уходить, и куда #

    Признаки, что Bash уже не тот инструмент - любого одного достаточно:

    • в задаче есть структуры данных или JSON сложнее плоского списка;
    • нужна арифметика с дробями;
    • нужна настоящая обработка ошибок с восстановлением;
    • параллелизм сложнее «N независимых задач»;
    • скрипт перевалил за триста строк и растёт;
    • его будут читать и править люди, которые Bash не знают.

    Куда. Python - когда нужны данные и библиотеки. Go или Rust - когда нужен один бинарник без зависимостей на целевой машине; Go дешевле по времени разработки, Rust - по надёжности в долгой эксплуатации, и для замены скрипта обычно решает первое. Make - когда задача про зависимости между шагами, а не про последовательность. Ansible или Terraform - когда задача про желаемое состояние, а не про действия.

    И обратное правило, не менее важное: двадцать строк на Bash не надо переписывать на Python ради принципа. Цена сопровождения растёт не от языка, а от размера.

Время потрачено не зря, если вы перестали спорить о языках вообще и начали называть конкретное свойство задачи: дроби, вложенные данные, восстановление после ошибки, размер. Это и есть перестройка нейросети - выбор инструмента перестаёт быть вопросом вкуса и становится вопросом цены, которую вы можете назвать вслух.

    1. Дыры set -e: условие, &&, функция из условия, подстановка в аргументе.
    2. Один тип данных и почему JSON в Bash всегда означает jq.
    3. Целочисленная арифметика и цена каждого bc.
    4. Параллелизм без синхронизации и граница применимости xargs -P.
    5. Порог трёхсот строк как практический сигнал.
    6. Две причины непереносимости: другая оболочка и другие утилиты.
    7. Список признаков ухода и куда уходить: Python, Go, Make, Ansible.
