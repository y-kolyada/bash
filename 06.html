    Практики в контексте AI

    Как работать с ИИ-агентом над shell-кодом: где он ошибается предсказуемо, как ставить задание, чем его проверять и чего ему не доверять.

    Главная мысль страницы #

    Языковая модель пишет Bash увереннее, чем точно, и ошибается она предсказуемо: кавычки, словоделение, потерянный код возврата, несуществующий ключ утилиты. Это не повод не пользоваться ею - это повод знать список мест, которые проверяют в первую очередь. Главная мысль страницы: пользу приносит не удачная формулировка задания, а наличие у агента петли самопроверки - shellcheck, bash -n и --dry-run стоят больше любого промпта, потому что промпт это надежда, а проверка это факт. Обратная сторона тоже верна: правильно написанный скрипт - лучшая форма инструмента для агента, если у него честный код возврата, разбираемый вывод и его можно запустить дважды.

    1 · Где модель ошибается в Bash, и почему именно там #

    Ошибки языковой модели в shell не случайны - они повторяются, и список короткий. Знание этого списка превращает проверку её работы из чтения всего кода в проверку пяти мест.

    # 1. незакавыченная подстановка
rm $file            # путь с пробелом

# 2. потерянный код возврата
grep x f | tee out  # вернёт 0

# 3. несуществующий ключ
sort --parallel=4   # нет в BSD

# 4. > вместо >>
echo a > log        # затёрло журнал

    Причина у всех одна: модель воспроизводит самый частый текст, а самый частый текст в интернете написан без строгого режима и без кавычек. Плюс она не знает вашей системы: GNU или BSD, bash или dash, какие утилиты установлены. Пятая типовая ошибка - уверенный вызов флага, которого в вашей версии утилиты нет.

    Что спрашивают: «Каким ошибкам ИИ в shell-коде вы не доверяете и проверяете в первую очередь?»

    2 · Как ставить задание на скрипт #

    Разница между «напиши скрипт для бэкапа» и работающим результатом - в трёх вещах, которые модель не может угадать: окружение, границы и признак готовности.

    Окружение: Ubuntu 22.04, bash 5.1,
GNU-утилиты, прав sudo нет.

Сделать: архив /var/app в /backup,
имя с датой, хранить 7 последних.

Границы: ничего не удалять вне
/backup; не ставить пакеты.

Готово, когда: shellcheck молчит,
--dry-run печатает план,
повторный запуск не ломает.

    Признак готовности - это предикат, и писать его надо до кода. Без него вы оцениваете результат по ощущению, а модель оптимизирует под то, чтобы выглядеть законченной. Три строки задания стоят получаса правок.

    Что спрашивают: «Что вы пишете в задании агенту, кроме самой задачи?»

    3 · Петля проверки дороже любого промпта #

    Главная мысль этой страницы: агент становится полезным не тогда, когда ему хорошо объяснили, а тогда, когда у него есть чем себя проверить. В Bash такая проверка существует и стоит дёшево.

    shellcheck -S warning script.sh \
  && bash -n script.sh \
  && ./script.sh --dry-run

    shellcheck ловит кавычки и коды возврата, bash -n - синтаксис без выполнения, --dry-run - логику без последствий. Три команды, которые агент запускает сам после каждой правки и исправляет найденное, дают больше, чем любая формулировка задания: промпт - это надежда, а проверка - факт.

    Что спрашивают: «Как устроена петля самопроверки у агента, пишущего скрипты?»

    4 · Чего агенту не доверяют #

    Опасность Bash для автоматики в том, что разрушительная команда ничем внешне не отличается от безобидной - ни по длине, ни по форме.

    rm -rf "$dir/"          # $dir пуст - беда
sudo anything           # прав быть не должно
curl … | bash           # код из сети сразу
> important.log         # затирание
git push --force        # чужая история

    Рабочее правило: агент предлагает, человек выполняет - для всего, что удаляет, повышает права, ходит в сеть за кодом или трогает общую историю. Технически это закрывается тремя мерами: обязательный --dry-run перед реальным запуском, запуск в контейнере или на копии данных, и явный список разрешённых команд вместо списка запрещённых.

    Что спрашивают: «Какие операции вы не разрешаете выполнять агенту автоматически и как это ограничиваете?»

    5 · Bash как хороший инструмент для агента #

    Обратная сторона: скрипт - лучшая форма инструмента для ИИ, если написан под машину, а не под человека.

    # машине нужен код возврата,
# а не слово "успешно"
check() {
  "$@" >/dev/null 2>&1 || return 1
}

# и разбираемый вывод
printf '%s\t%s\n' "$name" "$status"

    Три требования к такому инструменту: честный код возврата - ноль только при настоящем успехе; разбираемый вывод - колонки или JSON, а не фразы; идемпотентность - повторный запуск не ломает результат, потому что агент повторит, не спросив.

    Что спрашивают: «Каким должен быть скрипт, чтобы его мог надёжно вызывать агент?»

    6 · Как проверять то, что написала модель #

    Чтение диагонально не работает: код на Bash выглядит правдоподобно почти всегда. Проверка идёт по списку, и список короткий.

    # 1. есть ли строгий режим
# 2. закавычены ли все "$var"
# 3. честны ли коды возврата
# 4. что удаляет и чем ограничено
# 5. запустится ли дважды подряд

    И одно правило, которое дороже списка: попросите объяснить каждую строку, которую вы не понимаете. Если объяснение не сходится с тем, что делает команда, - это и есть найденный дефект. Непонятую строку не оставляют в скрипте: ответственность за неё всё равно ваша, а не модели.

    Что спрашивают: «Как вы принимаете shell-код, написанный ИИ, и что делаете со строкой, которую не понимаете?»

Это и есть перестройка нейросети: доверие заменяется процедурой, и работать с ИИ становится спокойнее, а не тревожнее.
