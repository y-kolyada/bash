    Практики SRE

    Триаж инцидента за минуту, скрытые отказы диска и памяти, разбор логов без добивания узла, защита продакшна от самих скриптов и метрики для мониторинга.

    Главная мысль страницы #

    Для SRE Bash - это инструмент первой минуты инцидента и одновременно главный источник рукотворных аварий, если эксплуатационный скрипт написан без тормозов. Когда узел деградирует, графики запаздывают, а агенты мониторинга могут уже лежать; на сломанной машине гарантированно есть только оболочка и директория /proc. Поэтому инженер держит в руках фиксированный маршрут триажа и знает ловушки ядра: почему место кончилось при полупустом du, почему kill -9 не берёт зомби и где искать след OOM-killer. Вторая половина работы SRE - сделать так, чтобы ремонтный скрипт, бэкап или цикл повторов сам не добил живую систему по диску, процессору и сети. И правило, отделяющее зрелую эксплуатацию от ремесла: скрипт, запускаемый по расписанию, обязан отдавать наружу свои метрики - иначе его тихую смерть заметят только по аварии.

    1 · Первая минута инцидента: чек-лист на живой машине #

    На сломанной машине, куда вы только что вошли по ssh, Bash незаменим: это единственное, что там гарантированно работает. Осмотр идёт по жёсткому маршруту, чтобы не тратить время на догадки.

    df -h; df -i; free -m    # диск, иноды, ОЗУ
uptime; vmstat 1 3       # очередь и CPU
ss -lntp | head -15      # кто слушает порт
systemctl is-active app  # жив ли юнит
journalctl -u app -n 50 --no-pager
ps -eo pid,stat,rss,cmd \
  --sort=-rss | head -6

    Порядок не случаен: место и индексные дескрипторы → память и своп → нагрузка и порты → статус сервиса и его журнал → самые тяжёлые процессы. В большинстве инцидентов причина находится на первых двух строках, поэтому начинать с чтения кода или перезапуска сервиса до осмотра ресурсов - ошибка.

    Что спрашивают: «С каких команд и в каком порядке вы начинаете разбор инцидента на незнакомом сервере?»

    2 · Скрытые отказы: почему df спорит с du, зомби и OOM #

    Три классических сценария на собеседованиях SRE - это ситуации, где стандартная команда показывает «норму» или не срабатывает, потому что причина лежит в ядре.

    # 1. df = 100%, а du видит свободное место
lsof +L1                 # удалён, но открыт
: > /proc/PID/fd/N      # освободить, не убивая
df -i                    # кончились иноды

# 2. процесс исчез без следа в логе приложения
dmesg -T | grep -i 'killed process'

# 3. зомби (Z) не убивается через kill -9
ps -eo pid,ppid,stat,cmd \
  | awk '$3 ~ /^Z/'

    Если лог-файл удалили через rm, пока процесс держит его дескриптор открытым, имя из каталога исчезает (du его не считает), но блоки на диске освободятся только после закрытия дескриптора. Если процесс перезапускать нельзя, файл усекают через его дескриптор: : > /proc/PID/fd/N. truncate -s 0 по старому имени не поможет: имени больше нет, и команда создаст рядом новый пустой файл, не освободив ни байта. Зомби-процесс (Z) уже мёртв и не занимает памяти - в таблице процессов осталась только запись с кодом возврата, пока родитель (PPID) не вызовет wait(); сигналить самому зомби бессмысленно.

    Что спрашивают: «Почему df -h показывает 100%, когда du -sh видит свободное место, и почему kill -9 не убивает зомби?»

    3 · Логи на живом узле: найти причину, не добив диск #

    Разбор гигабайтных журналов конвейером быстрее загрузки в стороннюю систему, если не сделать двух ошибок: не забить диск распаковкой и не зависнуть на буферизации трубы.

    # топ кодов или ошибок без имён файлов
grep -h ERROR /var/log/app/*.log \
  | awk '{print $5}' \
  | sort | uniq -c | sort -rn | head

# срез по времени и чтение архивов на лету
awk '/12:03:/,/12:06:/' app.log
zgrep -h '502 Bad' /var/log/nginx/*.gz

# поток вживую без задержки буфера
tail -f app.log \
  | grep --line-buffered ' 5[0-9][0-9] '

    Три детали решают исход: grep -h убирает префикс с именем файла, чтобы не сдвигать колонки в awk; --line-buffered заставляет grep сбрасывать каждую строку сразу, а не копить буфер на 4 КБ; zgrep и zcat читают сжатые логи потоком в памяти, не создавая временных файлов на переполненном разделе.

    Что спрашивают: «Как искать в ротированных архивах на переполненном диске и почему tail -f | grep долго молчит?»

    4 · Скрипт не должен положить прод: flock, nice и ionice #

    Тяжёлый скрипт обслуживания - архивация, ротация, сверка чек-сумм - запущенный на боевой машине с обычным приоритетом, отбирает диск и CPU у рабочего трафика и сам становится аварией.

    #!/usr/bin/env bash
set -euo pipefail

exec 9>/var/lock/backup.lock
flock -n 9 || exit 0   # второй не стартует

nice -n 19 ionice -c3 \
  tar -czf /backup/app.tgz /var/lib/app

    Два предохранителя обязательны для любой периодической задачи на узле. Первый - flock -n: если предыдущий запуск завис на медленном диске, следующий по cron не наложится поверх него лавиной из двадцати копий. Второй - nice -n 19 ionice -c3: класс Idle (-c3) отдаёт диску команды скрипта только тогда, когда ни один боевой процесс к диску не обращается.

    Оговорка, без которой это самообман: классы ionice соблюдает только планировщик BFQ (и CFQ в старых ядрах). При none и mq-deadline - частый выбор для NVMe и облачных дисков - ionice молча ничего не делает. Проверка - cat /sys/block/<диск>/queue/scheduler. Если там не BFQ, ограничивают не приоритет, а полосу: --bwlimit у rsync или IOWriteBandwidthMax= через systemd-run - это работает при любом планировщике.

    Что спрашивают: «Как защитить боевой сервер от деградации во время работы тяжёлого cron-скрипта?»

    5 · Каскадные отказы: backoff + jitter против шторма повторов #

    Когда внешний сервис или база начинает отвечать с ошибкой, две сотни узлов, повторяющих запрос в цикле через каждые две секунды, добивают сервис окончательно и не дают ему подняться.

    # случайный сдвиг старта в cron / скрипте
sleep $(( RANDOM % 30 ))

# экспоненциальная пауза + разброс (jitter)
retry() {
  local n
  for n in 1 2 3 4 5; do
    curl -sf --max-time 5 "$url" && return 0
    (( n == 5 )) && break
    sleep $(( (1 << n) + RANDOM % 5 ))
  done
  echo "сервис недоступен" >&2
  return 1
}
retry || exit 1

    Два правила для парков машин: расписание никогда не бьёт в секунду 00 одновременно (используют RandomizedDelaySec в systemd-таймерах или начальный сдвиг по RANDOM), а пауза между повторами растёт экспоненциально со случайной добавкой (jitter), чтобы рассинхронизировать волну запросов после сбоя. И цикл обязан закончиться честным отказом: без явного return 1 после последней попытки он вернёт код последней команды цикла, и полная недоступность сервиса будет выглядеть как успех.

    Что спрашивают: «Почему наивный цикл повторов в скрипте на парке серверов превращает кратковременный сбой в долгую аварию?»

    6 · Наблюдаемость скрипта и ловушка «самоисцеления» #

    Фоновый скрипт умирает двумя способами: падает с ошибкой или перестаёт запускаться вовсе. Если он пишет только в локальный лог, о потере бэкапов узнают в день, когда понадобится восстановление.

    t0=$SECONDS; rc=0
run_backup || rc=$?
dur=$(( SECONDS - t0 ))

prom=/var/lib/node_exporter/backup.prom
cat <<EOF > "$prom.$$"
backup_last_exit_code $rc
backup_duration_seconds $dur
backup_last_run_timestamp $(date +%s)
EOF
mv "$prom.$$" "$prom"   # атомарно

    Атомарная запись трёх чисел в textfile collector через временный файл и mv позволяет настроить два алерта: на ненулевой код и на устаревание метки времени (time() - backup_last_run_timestamp > 90000). И обратное правило SRE: скрипт «проверь и тихо перезапусти сервис» без счётчика и алерта вреден - он скрывает утечку памяти и деградацию вплоть до момента, когда перезапуск перестанет помогать.

    Что спрашивают: «Как мониторить выполнение фонового bash-скрипта и почему тихий авторестарт сервиса из cron опасен?»

    Чтение >> Ваш квант времени жизни · Партнёрство достоинства вместе с AI · Перестройка вашей нейросети

    Маршрут триажа и тормоза для автоматики. Время потрачено не зря, если при разборе аварии вы проверяете открытые удалённые дескрипторы и иноды раньше, чем перезапускаете сервис, а в каждый фоновый скрипт автоматически ставите неблокирующий flock, ionice и выгрузку метки времени. Это и есть перестройка нейросети: скрипт перестаёт быть невидимым для мониторинга и опасным для соседей по узлу.

    1. Маршрут первой минуты: диск и иноды, память, порты, юнит, журнал, тяжёлые процессы.
    2. Три ядерные ловушки: lsof +L1 и df -i при расхождении с du, OOM в dmesg, зомби в статусе Z.
    3. Разбор логов без вреда: grep -h, --line-buffered, zgrep без распаковки на диск.
    4. Изоляция нагрузки: flock -n от наложения запусков и nice / ionice -c3 для сохранения диска - и проверка, что планировщик это соблюдает.
    5. Защита от шторма: случайный сдвиг старта и exponential backoff + jitter.
    6. Метрики из скрипта: атомарная запись кода, длительности и времени в мониторинг через mv.
