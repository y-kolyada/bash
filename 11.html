    Примеры · IGL

    Шесть решений уровня «я решаю, появится ли скрипт вообще». Здесь код - иллюстрация к решению, а не наоборот: задача уровня - видеть цену решения на год вперёд.

    Главная мысль страницы #

    На этом уровне главный вопрос не «как написать», а «надо ли писать и чем мы заплатим». Самый дорогой скрипт в истории любой команды - тот, который успешно решил не ту задачу: взял на себя управление состоянием, обзавёлся собственным файлом состояния и собственными ошибками в нём. Шесть разборов ниже про решения, а не про приёмы: когда не писать вовсе; какой контракт объявить, если скрипт станет инструментом для машин; как пережить повторный запуск; что он обязан сообщать о себе; чем ограничен худший случай; и как вывести его из эксплуатации, когда придёт время. Последнее пропускают чаще всего - и именно оно отличает инженерное решение от технического.

    1 · Решение не писать скрипт #

    Ситуация: команда просит «небольшой скрипт», который будет следить за состоянием и чинить расхождения.

    # то, что просят:
# - проверить, что развёрнуто
# - сравнить с желаемым
# - довести до желаемого
# - запомнить, что сделал

# это описание Terraform,
# а не описание скрипта
    Почему так: Четыре требования выше - определение инструмента управления состоянием. Скрипт, который их выполняет, обязательно обзаведётся собственным файлом состояния, собственным сравнением и собственными ошибками в них. Решение уровня IGL здесь - не написать скрипт лучше, а назвать задачу своим именем и отдать её инструменту, у которого эта логика уже отлажена. Самый дорогой скрипт - тот, который успешно решил не ту задачу.

    2 · Контракт скрипта как инструмента #

    Ситуация: ваш скрипт будут вызывать другие скрипты, CI и агенты - то есть машины, а не люди.

    # контракт, который надо объявить:
# stdout  - только результат
# stderr  - всё остальное
# 0       - успех
# 1       - ожидаемый отказ
# 2       - неправильный вызов
# >=64    - внутренняя ошибка
# --json  - машинный вывод
# --dry-run - без последствий
    Почему так: У инструмента, который вызывают программы, контракт важнее реализации: реализацию можно переписать, контракт переписать нельзя - на него уже кто-то опирается. Коды возврата различают «не нашёл» и «сломался»: первое вызывающий обработает, второе должно остановить конвейер. Отдельный --json позволяет менять человеческий вывод, не ломая автоматику, - а без него любая правка текста становится ломающим изменением.

    3 · Устойчивость к повторам в распределённой среде #

    Ситуация: задача запускается планировщиком, который при таймауте запускает её ещё раз - не дожидаясь первой.

    # не идемпотентно:
echo "$line" >> report.txt
counter=$((counter + 1))

# идемпотентно:
key="run-$(date +%F)-$id"
grep -q "^$key" done.log || {
  work "$id"
  echo "$key" >> done.log
}
    Почему так: В распределённой среде повторный запуск - норма, а не исключение: таймауты, перезапуски узлов, двойные события. Защита не в том, чтобы запретить повтор, а в том, чтобы он ничего не менял. Ключевое решение здесь - ввести идентификатор операции и сделать работу условной от него. Обратите внимание на честную границу: grep плюс echo не атомарны, и при настоящей конкуренции нужна блокировка или внешнее хранилище - то есть сигнал, что задача выросла из скрипта.

    4 · Наблюдаемость: что скрипт обязан сообщать #

    Ситуация: скрипт работает ночью, и о его результате узнают через сутки.

    start=$(date +%s)
trap 'report "$?" "$start"' EXIT

report() {
  local rc=$1 t=$(( $(date +%s) - $2 ))
  printf 'result=%s rc=%s sec=%s items=%s\n' \
    "$([ "$rc" = 0 ] && echo ok || echo fail)" \
    "$rc" "$t" "$count" >&2
}
    Почему так: Скрипт без телеметрии виден только в момент отказа, и то если кто-то смотрит. Минимум из четырёх чисел - исход, код, длительность, объём работы - превращает его в наблюдаемый объект: по ним строится график, по графику видно деградацию до того, как она станет отказом. Строка в формате «ключ=значение» разбирается любым сборщиком логов без регулярных выражений. Вывод через ловушку EXIT гарантирует отчёт и при падении.

    5 · Радиус поражения: чем ограничено худшее #

    Ситуация: скрипт удаляет старые ресурсы. Вопрос не «работает ли он», а «что будет, когда он ошибётся».

    # запрет на работу вне своей области
case "$target" in
  /opt/app/releases/*) ;;
  *) echo "вне области: $target" >&2; exit 2 ;;
esac

# предел за один запуск
(( ${#list[@]} > 20 )) && { echo "слишком много" >&2; exit 2; }
    Почему так: Два ограничения стоят дороже любой аккуратности в коде. Белый список области делает невозможным удаление вне заданного пути - даже при пустой переменной, даже при ошибке в фильтре. Предел на объём за запуск превращает катастрофу в инцидент: скрипт, который «нашёл» три тысячи ресурсов вместо пяти, останавливается и зовёт человека. Это проектирование от худшего случая, а не от ожидаемого.

    6 · Вывод скрипта из эксплуатации #

    Ситуация: логика переезжает в инструмент, а скрипт остался и кем-то ещё вызывается.

    #!/usr/bin/env bash
echo "УСТАРЕЛО: используйте 'app deploy'" >&2
echo "этот скрипт перестанет работать 2026-12-01" >&2

exec app deploy "$@"   # пока - проксируем
    Почему так: Удалить скрипт одним днём нельзя: на него ссылаются чужие конвейеры, cron у соседней команды и чья-то память. Фаза проксирования с явной датой даёт время мигрировать и, главное, оставляет след в журналах - по ним видно, кто ещё вызывает. Дата в предупреждении обязательна: «устарело» без срока игнорируют бесконечно. Это та часть работы, которую пропускают чаще всего, и именно она отличает инженерное решение от технического.

    Артефакты: что у вас есть после этой страницы #

    Чтение >> Ваш квант времени жизни · Партнёрство достоинства вместе с AI · Перестройка вашей нейросети

    Шесть вопросов, которые задают до написания кода. Время потрачено не зря, если перед следующим скриптом вы спросите не «как это сделать», а «что будет, когда он ошибётся» и «кто его выключит». Это и есть перестройка нейросети: ответственность смещается с работоспособности на последствия, а это и есть граница между исполнителем и тем, кто принимает решения.

    1. Признак чужой задачи: проверить, сравнить, довести, запомнить - это инструмент состояния.
    2. Контракт инструмента: потоки, коды возврата, --json, --dry-run.
    3. Идентификатор операции как защита от повторного запуска.
    4. Четыре числа телеметрии: исход, код, длительность, объём.
    5. Белый список области и предел за запуск - проектирование от худшего случая.
    6. Фаза проксирования с датой при выводе из эксплуатации.
