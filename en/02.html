Glossary

    Writing scripts

    Rules and techniques separating a script that runs on your machine from one that runs on someone else's. And the boundary between the two modes of Bash, where half of all bugs originate.

    Key idea #

    A script differs from a sequence of commands not by length, but because it runs unattended. A human at a terminal sees an error and pauses; a script swallows it and plows ahead. Everything you kept in your head must be declared explicitly: strict mode, argument checks, clean up, and honest exit statuses. The second half of this page explores the line between an interactive shell and the script interpreter: they are different modes of the same program and read different startup files. Hence the classic “works in my terminal, fails in cron”, and the guiding rule: a script must never depend on your shell configuration. Everything else on this page follows from these two ideas.

    1 · Two modes: shell and interpreter #

    Bash is a single binary with two distinct roles, and half of the “unexplained” differences between a terminal and a script stem from this boundary. An interactive shell takes commands from a human: it maintains history, line editing, a prompt, and aliases. A script interpreter reads a file: it needs none of these conveniences and loads none of them.

    bash -c 'shopt -q login_shell; echo $?'
# 1 - not a login shell

echo $-            # no i in scripts
# hB  (interactive gives himBH)

    This leads to three consequences that most frequently cause bugs. Aliases do not work in scripts - expand_aliases is off by default for non-interactive shells. Scripts do not read ~/.bashrc: it is only read by an interactive non-login shell, which is why your PATH from .bashrc never reaches cron or CI. ~/.bash_profile is read only by login shells - SSH sessions, su -, or the first console.

    Practical takeaway: a script must not depend on your shell configuration. It must declare everything it needs itself - search paths, variables, and output locale.

    What gets asked: “Why does my alias or PATH work in the terminal but fail in a script or in cron?”

    2 · Skeleton: identical startup for every script #

    A good script always begins with the same five lines. They should be typed reflexively without thinking - save your thinking for what comes next.

    #!/usr/bin/env bash
set -euo pipefail
IFS=$'\n\t'

usage() { echo "usage: $0 <file>" >&2; exit 2; }
[ $# -eq 1 ] || usage

    env bash resolves whichever Bash executable is available on the machine, rather than assuming /bin/bash. set -euo pipefail provides three safety fuses: fail on error, fail on unset variable, do not lose a failure inside a pipeline. Narrowing IFS to newline and tab prevents splitting on spaces where it is almost never wanted.

    Argument validation is part of the skeleton, not decoration. A script run without arguments should state what it expects and exit with a non-zero code immediately, rather than failing on an empty variable midway through execution.

    What gets asked: “What does set -euo pipefail do and what does it not protect against?”

    3 · Functions and arguments #

    A variable inside a function is global by default. Without local, a function silently overwrites caller variables, which is notoriously hard to debug.

    greet() {
  local name="${1:?name required}"
  printf 'hello, %s\n' "$name"
}

# result - via stdout,
# status - via exit code
if out=$(greet "world"); then
  echo "$out"
fi

    Do not confuse the two channels: stdout is the result, exit status is the status. A function that prints “error” and returns 0 breaks every caller.

    "${1:?message}" marks a required argument: if absent, Bash halts the script with a clear message. For option parsing, use getopts; a custom loop with case is justified only for long options, which getopts cannot handle.

    What gets asked: “How does returning a value from a Bash function differ from return in other languages?”

    4 · Idempotence and cleanup #

    A script that cannot be run twice is only half a script. In production, re-execution is inevitable: by mistake, after a timeout, or on a CI retry.

    tmp=$(mktemp -d)
trap 'rm -rf "$tmp"' EXIT

mkdir -p /opt/app/releases
ln -sfn "$new" /opt/app/current

    mkdir -p, ln -sfn, rsync, install -D - these commands do not care whether the target state was already reached. Plain mkdir without -p and ln -s without -f do.

    A trap on EXIT is the only reliable cleanup: it fires on failure and on Ctrl+C alike. The temporary name must come from mktemp, not from you: a predictable name in /tmp is both a race condition and a security hole.

    What gets asked: “How do you make a script safe for repeated runs and ensure temporary files are cleaned up?”

    5 · Logging and diagnostics #

    Separating streams is not style, but a prerequisite for pipelines: results go to stdout, everything else to stderr. Otherwise your “[INFO] starting” message ends up in the data read by the next command.

    log() { printf '%s %s\n' "$(date +%T)" "$*" >&2; }

log "starting"
PS4='+ ${BASH_SOURCE}:${LINENO}: '
set -x          # enable tracing
set +x          # disable

    set -x prints each command after expansion - the fastest way to see what actually ran. PS4 adds the file and line number to the trace. Enabling tracing across an entire script in production is dangerous: variable values, including secrets, appear in the log.

    What gets asked: “Where should a script write its messages and why not stdout?”

    6 · Quality: shellcheck and formatting #

    Bash has a static analyzer that catches almost every common mistake before you run the script: unquoted expansions, useless cat, string comparisons where numbers were intended, cd without a check.

    shellcheck script.sh
shfmt -i 2 -w script.sh

# placed on the line immediately above:
# deliberate rule override:
# shellcheck disable=SC2086

    Overriding a rule is allowed, but only on the line directly above and with a comment explaining why. Disabling SC2086 globally means “we decided not to quote expansions”, and that decision should be stated out loud.

    For testing, there is bats. But the first test of any script is running with --dry-run: a mode where it prints what it would do and does nothing. Build it in from the start, not after the first incident.

    What gets asked: “How do you test shell scripts and what does shellcheck catch that humans miss?”
