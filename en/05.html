    Interconnections

    Where Bash interfaces with Git, CI, Docker, systemd, Make, and Ansible - and what breaks most often at each seam.

    Key idea #

    Bash rarely runs in isolation: it lives inside other tools, and most bugs arise at the boundary. A Git hook decides the fate of a commit via its exit status. CI executes steps with custom flags and a fresh process for each step. Docker string syntax sets PID 1 to a shell, preventing containers from stopping gracefully on signals. systemd parses ExecStart natively, without a shell. Make and Ansible execute each line in a separate shell process. Mastering these six boundaries resolves the core of assessment questions - and the majority of real-world production incidents.

    1 · Git: hooks and filters #

    Git lacks a built-in extension language: it launches executable files, and nearly always that means a shell script. A hook receives input via arguments or stdin and decides outcomes by exit status: non-zero aborts the operation.

    #!/usr/bin/env bash
# .git/hooks/pre-commit
set -euo pipefail

files=$(git diff --cached --name-only \
        --diff-filter=ACM | grep '\.sh$' || true)
[ -z "$files" ] && exit 0
shellcheck $files

    Two pitfalls. First: grep without matches exits with 1, which under set -e will crash the hook - hence || true. Second: hooks are not stored in the repository; the .git/hooks directory is unversioned. Consequently, version hooks in a dedicated folder and enable them via git config core.hooksPath, or teammates will never run them.

    What gets asked: “How do you make a hook reject a commit, and why do hooks not propagate to other developers automatically?”

    2 · CI and GitHub Actions: default shell #

    A run: step is a shell script written to a temporary file and executed by CI. Knowing the flags matters, and there is a subtle trap: without an explicit shell:, GitHub Actions runs bash -e {0} - set -e is active, but pipefail is absent. If you specify shell: bash explicitly, it runs as bash --noprofile --norc -eo pipefail {0} - pipefail is added. Neither variant enables -u.

    - name: build
  shell: bash          # gives -eo pipefail
  run: |
    set -euo pipefail  # supply own -u
    ./build.sh

# each step is a new process:
# export in one step is invisible
# to the next
echo "VER=1.2" >> "$GITHUB_ENV"

    Every step runs in a fresh process, so environment variables must be passed across steps via files ($GITHUB_ENV, $GITHUB_OUTPUT), not export. An extra warning: set -x inside a CI step prints variable expansions, exposing secrets in build logs - masking does not catch everything.

    What gets asked: “What flags does CI use to execute run: steps, and how do you persist values across steps?”

    3 · Docker: PID 1, signals, and syntax form #

    The most common ENTRYPOINT defect involves process hierarchy rather than shell syntax. In shell string form, the command runs via /bin/sh -c, and PID 1 belongs to the shell rather than your application - SIGTERM never reaches it, turning container stop into a forced SIGKILL timeout.

    # bad: PID 1 is sh
ENTRYPOINT /app/run.sh

# good: exec form
ENTRYPOINT ["/app/run.sh"]

# and in the script itself, at the end:
exec /app/server "$@"

    exec replaces the shell process with the application binary - PID 1 becomes the application, and signals arrive intact. Containers lack an init system, so zombie processes are never reaped; if your script spawns background tasks, use --init or tini. And remember Alpine: /bin/sh there is BusyBox ash, and bash is absent altogether.

    What gets asked: “Why does a container fail to stop on docker stop, and how does ENTRYPOINT syntax cause it?”

    4 · systemd: when a script is redundant #

    systemd handles natively much of what wrapper scripts were written for: automatic restarts, dependencies, resource limits, and logging. A wrapper that merely starts and restarts a service is superfluous.

    [Service]
ExecStart=/usr/bin/app --port 8080
Restart=on-failure
EnvironmentFile=/etc/app.env

# ExecStart is not a shell:
# neither $VAR, nor | , nor > work here
ExecStart=/bin/bash -c 'app | tee -a log'
# like this - only if strictly unavoidable

    The ExecStart directive is parsed directly by systemd, not a shell: variable substitutions, pipelines, and redirections do not work there. If strictly required, invoke bash -c explicitly and deliberately. Logs sent to stdout/stderr are ingested by journalctl; custom file rotation in scripts is almost always redundant work.

    What gets asked: “Why do redirections fail in ExecStart, and when is bash -c necessary?”

    5 · Make and Ansible: each line gets its own shell #

    A shared trap in both tools: lines do not share execution state. In Make, every recipe line runs in a separate subshell, meaning a cd in the first line has no effect on the second.

    # does not work:
build:
	cd src
	make all

# works:
build:
	cd src && make all

# or a single shell for the entire recipe:
.ONESHELL:

    In Ansible, the shell module similarly spins up a new shell instance for each task. Another frequent question: the command module executes binaries directly without a shell - no pipelines, substitutions, or globs; shell invokes an actual shell, with all features and all security risks. The rule: use command unless you have proven a shell is required.

    What gets asked: “Why does cd in a Makefile not persist into the next line, and how does command differ from shell in Ansible?”

    6 · Where Bash ends: jq, awk, Python #

    Ecosystem neighbors divide labor by data structure, and knowing the boundaries saves hours.

    # structured data - jq
jq -r '.items[] | select(.ok).id' f.json

# columns and arithmetic - awk
awk -F, '{s+=$3} END{print s/NR}' f.csv

# everything else - a real language
python3 -c 'import json, sys; ...'

    jq handles anything with nested hierarchies. awk handles line-oriented data with columns and arithmetic; it often replaces a pipeline of grep | cut | sort with a single process. Python takes over when you need third-party libraries, networking beyond curl, or stateful multi-step execution.

    Practical indicator: once a script contains a second jq invocation with a multi-line expression, the task has outgrown Bash.

    What gets asked: “When do you pick awk over a grep | cut pipeline, and when do you migrate to Python?”
