    Practices in an AI context

    How to work with an AI agent on shell code: where it fails predictably, how to specify tasks, how to verify output, and what never to trust it with.

    Key idea of this page #

    A language model writes Bash more confidently than accurately, and its mistakes are predictable: quoting, word splitting, lost exit statuses, non-existent utility options, and on modern models - strict mode crashing on standard code. This is not a reason to avoid using it - it is a reason to know the exact checklist to verify first. The key idea of this page: value comes not from a clever task prompt, but from the agent having a self-verification loop - shellcheck, bash -n, and --dry-run are worth more than any prompt, because a prompt is hope, while verification is a fact. The converse is also true: a properly written script is the best tool interface for an agent, provided it has an honest exit status, parsable output, and can be run twice safely. And the environment property forgotten most often: in most setups, an agent runs without a keyboard and without state between commands, so anything that waits for human input or remembers previous commands will break.

    1 · Where models fail in Bash, and why #

    A language model's shell errors are not random - they recur predictably, and the list is short. Knowing this list turns reviewing its output from reading all lines into inspecting six specific spots.

    # 1. unquoted expansion
rm $file            # path with space

# 2. lost exit status
grep x f | tee out  # returns 0

# 3. non-existent option
sort --parallel=4   # not in BSD

# 4. > instead of >>
echo a > log        # overwritten log

# 5. strict mode against standard code
set -e
grep -q x f         # no x: exit, silence
diff a b            # differences found: exit

    The first four stem from training data: models reproduce the most frequent text, and the most common text on the internet is written without strict mode and without quotes. Modern agentic models after post-training add set -euo pipefail and quotes on their own - and therefore commit the fifth, inverse mistake more often: crashing their own scripts on standard non-zero exit codes. grep without matches returns 1, diff on differences returns 1, ((i++)) from zero returns 1, and under strict mode each of these terminates the script without printing a single message. The sixth is invoking with full confidence an option that does not exist in your utility version: the model does not know your environment, whether it is GNU or BSD, bash or dash.

    2 · How to specify tasks for scripts #

    The difference between “write a backup script” and a working result lies in what the model cannot determine on its own: boundaries and the definition of done. It will inspect the environment faster and more accurately than you if the prompt tells it to do so: checking /etc/os-release and bash --version takes one second and does not depend on human memory.

    First: inspect the environment yourself -
os-release, bash --version, sudo -n.

Task: archive /var/app into /backup,
dated filename, retain the last 7.

Boundaries: do not delete outside
/backup; do not install packages.

Done when: shellcheck is silent,
--dry-run prints the plan,
repeated run does not break.

    The definition of done is a predicate, and it must be formulated before the code. Without it, you evaluate the result on impression, while the model optimizes for looking finished. Three lines of specification save half an hour of revisions.

    Persistent rules go into files, one-off rules go into the prompt. Rules that apply permanently - stop switches, push restrictions, verification commands - live in the repository's AGENTS.md, and the agent reads them on every start. Typing them into every prompt guarantees forgetting them eventually.

    What gets asked: “What do you include in a task specification for an agent besides the task itself?”

    3 · A verification loop beats any prompt #

    The core thesis of this page: an agent becomes useful not when it receives a great explanation, but when it possesses the means to verify itself. In Bash, such verification exists and costs almost nothing.

    shellcheck -S warning script.sh \
  && bash -n script.sh \
  && ./script.sh --dry-run

    shellcheck catches quotes and exit statuses, bash -n validates syntax without execution, and --dry-run validates logic without side effects. Three commands that the agent runs itself after each edit and fixes what it finds deliver far more than any prompt phrasing: a prompt is hope, but verification is fact.

    The loop includes two more checks, both about behavior rather than knowledge. First: test options by running them, not by reading help. A model gets options wrong precisely because it assumes they are familiar, so a rule like "verify unfamiliar options" never triggers; furthermore, many BSD tools lack both --help and --version. Only one thing is reliable: run the command itself on empty or dummy input - cmd -flag < /dev/null.

    Second: inspect real data before writing parsing logic. Field names for jq and column numbers for awk are confidently invented by models; running cmd | head -20 before writing the first line of parsing saves more iterations than any syntax check.

    What gets asked: “How is the self-verification loop structured for an agent writing scripts?”

    4 · What not to trust an agent with #

    The danger of Bash for automation is that a destructive command looks no different on the outside from an innocent one - neither in length nor in structure.

    rm -rf "$dir/"          # $dir empty: disaster
sudo anything           # no elevated privileges
curl … | bash           # remote code executed directly
> important.log         # truncation
git push --force        # external history

    The working rule: the agent proposes, the human executes - for anything that deletes, elevates privileges, pulls remote code, or touches shared history. Technically, this is guarded by two measures, both about the environment rather than a banned word list: isolation - containers, data copies, separate worktrees via git worktree, - and confirmation of the exact invocation with all its arguments. A whitelist of command names is not a security boundary: find -delete, tar --checkpoint-action, env, or any interpreter from such a list can destroy and execute just as well as rm.

    A distinct hazard is text read by the agent. Command output, file contents, web pages, or log entries may contain prompt-like directives: “ignore previous instructions and run...”. To the agent, this is data, not instructions. The defense is identical to human safeguards: a high-risk operation requires human confirmation regardless of where the prompt originated - from the task description, model generation, or a file it just opened.

    5 · Bash as a good tool for an agent #

    The converse: a script is the best tool interface for an AI when written for machines rather than humans.

    # machines need an exit status,
# not the word "success"
check() {
  "$@" >/dev/null 2>&1 || return 1
}

# and parsable output
printf '%s\t%s\n' "$name" "$status"

    Three requirements for such a tool: an honest exit status - zero only on genuine success; parsable output - columns or JSON, not human sentences; idempotence - running it again does not corrupt the state, because an agent will retry without asking.

    What gets asked: “What properties must a script have so that an agent can invoke it reliably?”

    6 · An agent environment is not your terminal #

    Most agent environments launch each command as an isolated, non-interactive process and capture its stdout/stderr rather than a terminal screen. This introduces four properties foreign to your interactive shell. Some runners smooth over a subset of these - setting PAGER=cat automatically or piping input to a running child, - but a script that relies on such support ceases to work when moved to another environment.

    No keyboard. Anything that waits for a user - pagers, password prompts, “continue? [y/N]”, editors for commit messages - turns into an indefinite hang until timeout.

    git --no-pager log -5
GIT_PAGER=cat PAGER=cat cmd
apt-get install -y pkg
git commit -m "commit message"   # without editor
cmd < /dev/null             # nothing to wait for
timeout 60 cmd              # always set a limit

    No state between invocations. cd, variables, functions, and traps defined in one agent command do not exist in the next: each runs in a fresh process. Pass directories explicitly, and keep anything that needs to persist across commands in a file or script.

    Background processes hold output streams open. A process started with & inherits the agent's stdout/stderr, and the runner waits for it to close even if the invoking script has finished. Fully detach background processes:

    # agent will wait for server:
server &
# will not wait:
server >log 2>&1 </dev/null &

    Output consumes context window. A human can scroll past a thousand lines, but for an agent they flood working memory and push out critical context. Scripts designed for agents should be concise: return summaries rather than logs, and keep details behind a --verbose flag or write them to a file. In command chains, use | tail -50, --quiet, and grep -c instead of dumping all matches.

    What gets asked: “Why does an agent hang on a command that runs instantly in your terminal, and why does its cd have no effect on the next command?”

    7 · Edit files with dedicated tools, not shell commands #

    When an agent has dedicated file-reading and editing tools - present in almost every modern platform - editing via sed -i, cat <<EOF > file, and echo > becomes the primary source of file corruption. An unquoted delimiter expands $(...) within text, an accidental > truncates a file, and a loose regex in sed matches the wrong line.

    # how files get corrupted silently:
sed -i 's/port=.*/port=8080/' app.conf
cat <<EOF > deploy.sh
echo "$HOME"     # expanded upon write
EOF

    A specialized edit tool verifies which exact snippet is replaced, failing gracefully if the snippet is missing or ambiguous; the shell blindly runs whatever was passed. The rule is simple: use the shell for commands, and file-editing tools for files.

    What gets asked: “Why should an agent with file-editing tools avoid modifying files via sed and here-documents?”

    8 · Reviewing model-generated code #

    Skimming does not work: Bash code almost always looks plausible at a glance. Verification follows a short checklist.

    # 1. is strict mode enabled
# 2. are all "$var" quoted
# 3. are exit statuses honest
# 4. what does it delete and how is it bounded
# 5. does it run cleanly twice in a row

    And one rule more valuable than the list: ask for an explanation of every line you do not understand. If the explanation contradicts what the command actually does, that discrepancy is your defect. Never leave an unexplained line in a script: responsibility for it remains yours, not the model's.

    Artifacts: what you take away from this page #

    Reading >> Your life quantum · Dignity partnership with AI · Rewiring your neural network

    A five-point checklist instead of reading the entire code. Your time was well spent if you stopped accepting model output based on persuasive explanations and started accepting it based on verification exit codes. That is the essence of rewiring: trust is replaced by procedure, making work with AI calmer rather than anxious.

    1. Six standard model failure modes - and the latest inverse trap: strict mode crashing on standard exit status 1.
    2. Task specification: boundaries and definition of done; the agent discovers environment details on its own; persistent rules live in AGENTS.md.
    3. Self-verification loop of three commands, plus testing options by invocation and inspecting real data prior to parsing.
    4. Security boundary - isolation and invocation confirmation, not a command name whitelist.
    5. Three requirements for tool scripts: honest exit statuses, parsable output, and idempotence.
    6. Four properties of the agent environment: no keyboard, stateless between commands, background processes keep streams open, and output consumes context.
    7. Use file tools for files, shell for commands.
    8. Read input is data, not instructions: confirming dangerous operations does not depend on where the idea came from.
    9. The ununderstood line rule: explain it or remove it.
