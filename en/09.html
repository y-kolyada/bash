    Practices SRE

    Words: 1386

    Incident triage in sixty seconds, hidden disk and memory failures, parsing logs without killing the node, protecting production from scripts themselves, and monitoring metrics.

    Key idea of this page #

    For an SRE, Bash is both the first-minute incident response tool and the primary source of self-inflicted outages when maintenance scripts lack safeguards. When a node degrades, monitoring dashboards lag and agents may already be dead; on a damaged host, only the shell and /proc are guaranteed to work. An engineer must follow a rigorous triage routine and understand kernel traps: why disk space runs out when du shows gigabytes free, why kill -9 cannot touch a zombie, and where to find traces of the OOM killer. The other half of SRE work is ensuring that repair scripts, backups, or retry loops do not overwhelm a struggling system across disk, CPU, or network. And the rule separating mature operations from amateur craft: any scheduled script must expose its metrics - otherwise its silent failure will only be discovered during an outage.

    1 · The first minute of an incident: live server checklist #

    On a malfunctioning host reached via ssh, Bash is indispensable: it is the only tool guaranteed to be functional. Inspection follows a strict path to avoid wasting time on guesswork.

    df -h; df -i; free -m    # disk, inodes, RAM
uptime; vmstat 1 3       # queue and CPU
ss -lntp | head -15      # listening ports
systemctl is-active app  # is unit alive
journalctl -u app -n 50 --no-pager
ps -eo pid,stat,rss,cmd \
  --sort=-rss | head -6

    The sequence is intentional: disk space and inodes → RAM and swap → load queue and ports → service unit status and logs → heaviest processes. In most incidents, the root cause is uncovered in the first two lines, making diving into application code or restarting services before inspecting system resources a critical mistake.

    What gets asked: “Which commands and in what order do you execute when triaging an incident on an unfamiliar server?”

    2 · Hidden failures: why df contradicts du, zombies, and OOM #

    Three classic SRE interview scenarios where standard commands show normal status or fail because the mechanism resides in the kernel.

    # 1. df = 100%, but du sees free space
lsof +L1                 # deleted but open
: > /proc/PID/fd/N      # truncate without killing
df -i                    # out of inodes

# 2. process vanished without trace in app logs
dmesg -T | grep -i 'killed process'

# 3. zombie (Z) cannot be killed with kill -9
ps -eo pid,ppid,stat,cmd \
  | awk '$3 ~ /^Z/'

    If a log file is removed via rm while an active process holds its file descriptor open, the directory entry vanishes (du ignores it), but disk blocks remain allocated until the descriptor is closed. If restarting the process is not an option, truncate the file via its open descriptor: : > /proc/PID/fd/N. truncate -s 0 on the old filename will not help: the name no longer exists, and the command creates a new empty file alongside without freeing a single byte. A zombie process (Z) is already dead and consumes no memory - it is merely a process table entry retaining an exit code until its parent (PPID) invokes wait(); sending signals to a zombie is entirely ineffective.

    What gets asked: “Why does df -h show 100% when du -sh shows free space, and why can't kill -9 terminate a zombie?”

    3 · Logs on a live node: root cause analysis without exhausting disk #

    Piping multi-gigabyte logs through a shell pipeline is faster than shipping them to external platforms, provided two traps are avoided: filling the disk with uncompressed archives and stalling on pipe buffering.

    # top error codes without filenames
grep -h ERROR /var/log/app/*.log \
  | awk '{print $5}' \
  | sort | uniq -c | sort -rn | head

# time slice and reading compressed logs on the fly
awk '/12:03:/,/12:06:/' app.log
zgrep -h '502 Bad' /var/log/nginx/*.gz

# live stream without pipe buffer delay
tail -f app.log \
  | grep --line-buffered ' 5[0-9][0-9] '

    Three details decide the outcome: grep -h suppresses filename prefixes so awk column positions stay stable; --line-buffered forces grep to flush each matching line immediately rather than filling a 4 KB buffer; zgrep and zcat stream compressed archives directly through memory without staging temporary files on a full disk partition.

    What gets asked: “How do you search rotated compressed logs on a full disk, and why does tail -f | grep often produce no immediate output?”

    4 · Scripts must not crash production: flock, nice, and ionice #

    A heavy maintenance script - archiving, rotating, or checksumming - running on production with standard priority starves customer traffic of disk and CPU, triggering an outage on its own.

    #!/usr/bin/env bash
set -euo pipefail

exec 9>/var/lock/backup.lock
flock -n 9 || exit 0   # second instance exits

nice -n 19 ionice -c3 \
  tar -czf /backup/app.tgz /var/lib/app

    Two safeguards are mandatory for any periodic task on a node. First: flock -n - if a previous run hangs on a slow disk, the next cron trigger will not pile up into a thundering herd of twenty concurrent processes. Second: nice -n 19 ionice -c3 - the Idle class (-c3) submits I/O requests to disk only when no production workload needs the disk.

    The essential caveat: ionice priority classes are honored only by the BFQ I/O scheduler (and legacy CFQ). Under none or mq-deadline - typical for NVMe and cloud volumes - ionice is silently ignored. Verify via cat /sys/block/<disk>/queue/scheduler. When BFQ is absent, throttle bandwidth instead: --bwlimit in rsync or IOWriteBandwidthMax= via systemd-run - which works under any I/O scheduler.

    What gets asked: “How do you protect a production node from degradation during heavy cron jobs?”

    5 · Cascading failures: backoff + jitter against retry storms #

    When an upstream service or database begins throwing errors, two hundred nodes retrying requests in a tight loop every two seconds exhaust the service completely, preventing any recovery.

    # random start jitter in cron / script
sleep $(( RANDOM % 30 ))

# exponential backoff + jitter
retry() {
  local n
  for n in 1 2 3 4 5; do
    curl -sf --max-time 5 "$url" && return 0
    (( n == 5 )) && break
    sleep $(( (1 << n) + RANDOM % 5 ))
  done
  echo "service unavailable" >&2
  return 1
}
retry || exit 1

    Two fleet rules: scheduled jobs must never trigger simultaneously at second 00 (use RandomizedDelaySec in systemd timers or initial delay via RANDOM), and intervals between retries must increase exponentially with random jitter (jitter) to desynchronize request waves after an outage. The loop must terminate with an honest exit code: without an explicit return 1 after the final failed attempt, it returns the exit status of the loop test, disguising complete upstream failure as success.

    What gets asked: “Why does a naive retry loop on a fleet turn a transient hiccup into a prolonged outage?”

    6 · Script observability and the self-healing anti-pattern #

    A background script fails in two ways: it exits with an error or stops running entirely. If it writes exclusively to local logs, backup failures will only be discovered on the day recovery is required.

    t0=$SECONDS; rc=0
run_backup || rc=$?
dur=$(( SECONDS - t0 ))

prom=/var/lib/node_exporter/backup.prom
cat <<EOF > "$prom.$$"
backup_last_exit_code $rc
backup_duration_seconds $dur
backup_last_run_timestamp $(date +%s)
EOF
mv "$prom.$$" "$prom"   # atomic cutover

    Writing three numbers atomically into the Prometheus textfile collector via a temporary file and mv enables two critical alerts: non-zero exit codes and stale timestamps (time() - backup_last_run_timestamp > 90000). And the counter-rule of SRE: a script that silently restarts a failing service without recording metrics or raising alerts is harmful - it masks memory leaks and progressive degradation until restarts no longer recover the service.

    What gets asked: “How do you monitor background shell script execution, and why is silent service auto-restarting dangerous?”

    A triage route and safeguards for automation. Your time was well spent if during incident triage you inspect unlinked open file descriptors and inode saturation before restarting services, and automatically equip every background script with non-blocking flock, ionice, and timestamp metrics. That is the essence of rewiring: scripts cease being invisible to monitoring and dangerous to neighboring processes.

    1. First-minute triage sequence: disk and inodes, memory, ports, unit status, journal, heavy processes.
    2. Three kernel traps: lsof +L1 and df -i when diverging from du, OOM in dmesg, and zombies in status Z.
    3. Non-destructive log inspection: grep -h, --line-buffered, and streaming zgrep without disk extraction.
    4. Workload isolation: non-blocking flock -n against overlap, nice / ionice -c3 for I/O pacing, and verifying scheduler compliance.
    5. Storm prevention: randomized startup jitter and exponential backoff + jitter.
    6. Script metrics: atomic emission of exit code, duration, and timestamp via mv.
