    Examples · Noob

    Words: 803

    Six breakdowns for the “I run and occasionally tweak scripts” level. The goal of this level is to remove magic: every line here is explained down to root cause, not just as a recipe.

    Key idea of this page #

    At this level, what matters is not the number of commands memorized, but understanding why a script behaves the way it does. The six walkthroughs below address where beginners stumble most frequently: script file execution and permissions, variable quoting, validating before acting, file looping, arguments and exit statuses, and reading files line by line. Each walkthrough presents the task, then the code, then the explanation - and the explanation is the key takeaway. You can learn these six patterns in an evening; truly understanding them means never fearing someone else's script again.

    1 · Your first script: file, permissions, execution #

    Task: Turn two commands into an executable program.

    #!/usr/bin/env bash
echo "today: $(date +%F)"
df -h / | tail -1
    chmod +x hello.sh   # once
./hello.sh          # execute
bash hello.sh       # without execute permission
    Why this works: A script file is ordinary text; the permission bit makes it executable, not the file extension. The ./ prefix is mandatory: without it, the shell searches PATH, which does not include the current directory - resulting in “command not found” for a file sitting right beside you. bash hello.sh works without execute permissions because bash itself executes, taking the script as a file argument.

    2 · Variables and quotes #

    Task: Output a filename containing a space.

    file="my report.txt"

echo $file     # my report.txt - lucky
ls $file       # ERROR: two files
ls "$file"     # correct

rm -f $file    # deletes "my" and "report.txt"
    Why this works: Bash expands the variable value and then splits it on whitespace. echo masks this because it prints all arguments separated by spaces - creating a false impression that everything worked. Quotes prevent word splitting. The rule is simple: unquoted expansion must be an intentional decision, never the default.

    3 · Conditions: check before acting #

    Task: Copy a file if it exists; otherwise clearly report the failure.

    src="data.csv"

if [ -f "$src" ]; then
  cp "$src" backup/
else
  echo "missing file: $src" >&2
  exit 1
fi
    Why this works: [ -f ] checks for an existing regular file; -d tests for a directory, -r for readability, and -z for an empty string. Error messages must go to >&2 - to stderr, not standard output. And exiting with a non-zero code is mandatory: without it, callers assume the script succeeded.

    4 · Looping over files (and why not to use ls) #

    Task: Process all .log files in a directory.

    # correct
for f in *.log; do
  [ -e "$f" ] || continue   # none found
  echo "processing: $f"
done

# incorrect, yet common
for f in $(ls *.log); do
  echo "processing: $f"
done
    Why this works: The glob pattern *.log is expanded directly by the shell, preserving full filenames intact - even with embedded spaces. $(ls) outputs a single string that is subjected to word splitting, turning “old file.log” into two non-existent paths. The check [ -e "$f" ] is essential: if no files match, the glob remains as a literal string, causing the loop to run once with the literal string *.log.

    5 · Arguments and exit status #

    Task: Accept a name from the user and report whether the operation succeeded.

    #!/usr/bin/env bash
name="$1"

if [ -z "$name" ]; then
  echo "usage: $0 <name>" >&2
  exit 2
fi

grep -q "$name" users.txt
echo "exit code: $?"
    Why this works: $1 is the first positional argument, $# is the argument count, and $0 is the script name. $? holds the exit status of the most recently executed command, serving as the sole mechanism to determine whether a command succeeded: grep returns 0 on match and 1 on no match. Zero signifies success; any non-zero value indicates failure. Exit code 2 conventionally denotes invalid invocation.

    6 · Reading files line by line #

    Task: Iterate through the lines of a file and process each.

    while IFS= read -r line; do
  echo "line: $line"
done < names.txt
    Why this works: Three necessary details. IFS= before read prevents stripping leading and trailing whitespace. -r disables backslash escape interpretation - without it, C:\new turns into a string with an embedded newline. And the input redirection < file belongs after done, not before while.
