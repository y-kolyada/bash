    Examples · IGL

    Six decisions for the “I decide whether a script should exist at all” level. Here code illustrates the decision rather than the reverse: the task of this level is forecasting the total cost of ownership one year out.

    Key idea of this page #

    At this level, the primary question is not “how to write it,” but “should we write it, and what will it cost us down the road.” The most expensive script in any team's history is the one that successfully solved the wrong problem: taking on state management, acquiring a custom state file, and accumulating custom state reconciliation bugs. The six analyses below focus on architectural choices rather than syntax: when to refuse to write a script; what interface contract to establish when a script becomes a machine-callable tool; how to survive retries in distributed environments; what telemetry a script must emit; how to bound worst-case blast radius; and how to safely decommission a script when its lifecycle ends. That final decommissioning step is skipped most often - yet it is what separates engineering discipline from ad-hoc scripting. Each case study includes a “Decision cost” analysis: the cost of implementing versus the cost of avoiding.

    1 · The decision not to write a script #

    Situation: The team requests a “quick script” to monitor state and reconcile drift.

    # what is requested:
# - inspect what is deployed
# - diff against desired state
# - converge to desired state
# - record actions taken

# this describes Terraform,
# not a shell script
    Why this matters: The four requirements above define a state management tool. Any shell script implementing them will inevitably accumulate custom state storage, bespoke diff algorithms, and distinct failure modes. The IGL decision here is not writing a cleaner script, but calling the task by its true name and delegating it to an established tool where reconciliation logic is already hardened. The costliest script is the one that successfully solves the wrong problem.
    Decision cost: Declining costs a single conversation and perhaps a week evaluating a dedicated tool. Agreeing commits to indefinite maintenance of an in-house state management engine - with costs scaling directly with managed resource count.

    2 · Tool contract: scripts for machines #

    Situation: Your script will be invoked by downstream scripts, CI pipelines, and automated agents - machines rather than humans.

    # contract to declare explicitly:
# stdout   - results only
# stderr   - all diagnostics and logs
# 0        - success
# 1        - expected domain failure
# 2        - invalid command invocation
# 3-63     - custom codes, documented in --help
# 126, 127, 128+N - reserved by shell
# --json   - machine-readable output
# --dry-run - non-destructive execution
    Why this matters: For a machine-facing tool, interface contracts supersede internal implementation: implementations can be refactored freely, but breaking an established contract breaks dependent automation. Exit codes must distinguish “not found” from “crashed”: callers can handle the former cleanly, while the latter must halt pipelines. Providing a dedicated --json flag allows iterating on human-readable text without disrupting parsers; without it, any formatting polish is a breaking API change. For standardized exit code conventions, reference sysexits.h: 64 for command line syntax errors, 70 for internal software bugs, 75 for transient failures suitable for retries. Never assign custom meanings to 126, 127, or 128+N: these are emitted by the shell itself, and callers will be unable to distinguish your error code from “permission denied”, “command not found”, or “terminated by signal”.
    Decision cost: Formalizing the contract costs thirty minutes and a dozen lines in --help. Omitting it turns every future output edit into an outage for callers you may not even know exist.

    3 · Idempotence and retry resilience in distributed environments #

    Situation: A job is triggered by a scheduler that upon hitting a timeout fires a retry without waiting for the prior run to complete.

    # not idempotent:
echo "$line" >> report.txt
counter=$((counter + 1))

# idempotent:
key="run-$(date +%F)-$id"
grep -q "^$key" done.log || {
  work "$id"
  echo "$key" >> done.log
}
    Why this matters: In distributed environments, retries are expected operational reality, not edge cases: network timeouts, node rescheduling, and duplicate webhook events occur constantly. Resilience means ensuring duplicate invocations do not corrupt state. The architectural decision is introducing an idempotency key and conditioning mutations upon it. Note the architectural boundary: grep followed by echo is not atomic; true concurrency requires filesystem locking or external transactional storage - signaling that the task has outgrown plain shell scripts.
    Decision cost: An idempotency key and completion log require ten lines. Without them, scheduler retries produce duplicate billings, duplicate notification blasts, or destructive repeated deletions.

    4 · Observability: what scripts must emit #

    Situation: A script runs unattended overnight, and its outcome is only reviewed twenty-four hours later.

    start=$(date +%s)
trap 'report "$?" "$start"' EXIT

report() {
  local rc=$1 t=$(( $(date +%s) - $2 ))
  printf 'result=%s rc=%s sec=%s items=%s\n' \
    "$([ "$rc" = 0 ] && echo ok || echo fail)" \
    "$rc" "$t" "$count" >&2
}
    Why this matters: An uninstrumented script is only noticeable when it crashes outright - and only if someone is watching. A minimum telemetry payload of four metrics - outcome, exit code, elapsed duration, and processed volume - turns it into an observable component: metrics can be trended, revealing performance degradation long before catastrophic outage. Structured key=value lines parse natively across log aggregators without complex regular expressions. Emitting telemetry from an EXIT trap guarantees reports even during unhandled script crashes.
    Decision cost: One structured line emitted per execution. Without it, performance degradation remains hidden until complete failure occurs - usually discovered by customers first.

    5 · Blast radius: bounding worst-case failure modes #

    Situation: A script purges aged resources. The question is not “does it work,” but “what happens when its logic fails.”

    # restrict execution outside allowed scope
case "$target" in
  /opt/app/releases/*) ;;
  *) echo "out of scope: $target" >&2; exit 2 ;;
esac

# cap work per single invocation
if (( ${#list[@]} > 20 )); then
  echo "too many items" >&2
  exit 2
fi
    Why this matters: Two safety guards outweigh any amount of careful coding. Scope whitelisting prevents mutations outside designated filesystem trees - even under empty variables or regex evaluation bugs. Per-run batch limits downgrade potential catastrophes into routine operational tickets: a script that resolves three thousand purge candidates instead of five aborts immediately and demands human review. This is designing for the worst-case scenario rather than the happy path.
    Decision cost: Two validation checks at script initialization. Without them, a single filtering typo risks destroying everything within the script's ambient IAM permissions.

    6 · Decommissioning scripts gracefully #

    Situation: Legacy script functionality has migrated into a platform tool, but dependent callers continue invoking the original entry point.

    #!/usr/bin/env bash
echo "DEPRECATED: use 'app deploy'" >&2
echo "this script will be decommissioned 2026-12-01" >&2

exec app deploy "$@"   # proxying for now
    Why this matters: You cannot delete a shared script overnight: dependent CI jobs, external cron schedules, and muscle memory remain active across teams. A proxying deprecation phase with a definitive sunset date affords calling teams time to migrate while surfacing remaining consumers in audit logs. Specific sunset dates are essential: open-ended “deprecated” warnings are ignored indefinitely. This operational discipline is what elevates software engineering above raw scripting.
    Decision cost: A month of proxying and reviewing invocation logs. Skipping this step guarantees breaking uncataloged dependencies on the day of removal.

Your time was well spent if before approving your next script you ask “what happens when its filter fails” and “who will decommission this when it is superseded.” That is the essence of rewiring: accountability shifts from immediate functionality to long-term blast radius, defining the boundary between an implementer and a technical lead.
