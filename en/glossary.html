    Glossary

    Twenty-two concepts that the site's pages will not stop to explain again. None of them is an exam definition - each is a mechanism whose absence costs an incident.

    The key idea of this glossary #

    This glossary exists to eliminate ambiguity rather than to be memorized: as long as “an error” and “a non-zero exit code” mean different things to you, debating script reliability is pointless. Concepts are arranged across three tiers, mirroring the structure of the site itself: mechanics - how the shell executes a command line; practice - how to write scripts that survive production; decisions - how the worst case is bounded. Each card has three layers: a single sentence for immediate recognition, a paragraph explaining the underlying mechanism, and a link to the section where the concept is explored in detail. The cards are deliberately concise: density beats completeness, and the complete description is in man bash.

    Mechanics: how the shell executes a command line #

    Shebang #!/usr/bin/env bash #

    The first line of a script, instructing the kernel which interpreter to execute it with.

    Without it, the script runs in whichever shell invoked it - and on a machine where sh is dash, arrays and [[ ]] stop working. The env form searches for bash in PATH rather than only in /bin: on macOS and the BSDs it resides in a different location.

    First seen in: Writing scripts · Skeleton

    Shell modes login · interactive #

    A single Bash program in two roles: an interactive shell used by a human, and an interpreter executing a file.

    An interactive shell reads ~/.bashrc, enables aliases, and maintains history; a login shell (SSH sessions, su -) reads ~/.bash_profile; a non-interactive script reads neither. Hence "it works in my terminal, but fails in cron": PATH and aliases from your profile files never reach the script.

    First seen in: Writing scripts · Two modes

    PATH $PATH #

    A colon-separated list of directories where the shell searches for executables by name.

    The current directory is not included, which is why a local script must be run as ./script.sh. Order matters: the first matching executable is executed, and type cmd reveals which one it is. In cron and CI environments, PATH is typically shorter than in your interactive shell - a script relying on implicit locations will fail there first.

    First seen in: Examples · Noob · First script

    Environment variable export VAR=value #

    A variable exported by the shell to child processes.

    A standard assignment VAR=value remains visible only within the current shell process; export marks the variable for inheritance. Inheritance flows strictly downward: a child process cannot modify its parent process's environment. That is why values set in one CI step do not persist into the next - each step runs in a separate process.

    First seen in: Key components · Variables

    Glob *.log · ?.txt · [ab]* #

    An expression expanded by the shell into matching filenames before executing the command.

    Filename expansion is performed by the shell itself rather than the utility, preserving filenames containing whitespace intact - unlike parsing $(ls). If no file matches, by default the pattern remains a literal string, and a loop executes once with *.log; shopt -s nullglob changes this behavior to expand to an empty list instead.

    First seen in: Key components · Command line parsing

    Word splitting "$var" #

    Dividing unquoted expansion results into distinct words based on whitespace and newlines.

    Bash substitutes the variable value and then splits it on delimiter characters. Consequently, an unquoted path like /home/My Files/a.txt is split into two separate arguments, causing a delete command to remove unintended files. Enclosing expansions in double quotes is not a style preference but a defensive necessity - and it remains the most common error made by AI coding agents.

    First seen in: Key components · Expansions and word splitting

    IFS IFS=$'\n\t' #

    The Internal Field Separator: the set of characters the shell uses to split text into words.

    By default, it contains space, tab, and newline. Restricting IFS to newline and tab at the start of a script prevents unwanted splitting on spaces where it is rarely intended. In the idiom IFS= read -r line, the assignment applies only to the single command, preserving leading and trailing whitespace.

    First seen in: Key components · Expansions and word splitting

    Stream and file descriptor 0 · 1 · 2 #

    A numbered input or output channel for a process: 0 is standard input, 1 is standard output, 2 is standard error.

    A file descriptor is an integer; a stream is the data flowing through it. Separating stdout (1) and stderr (2) is a fundamental prerequisite for pipelines: downstream commands read only stream 1, so informational messages printed there pollute pipeline data. Hence the rule: data goes to stdout, operational logging to stderr, execution status to the exit code.

    First seen in: Key components · Processes and redirections

    Redirection > · >> · 2>&1 #

    Instructing the shell to redirect a process stream away from the default terminal.

    > truncates and overwrites a file, >> appends to it, and 2>&1 redirects standard error to wherever standard output is currently directed. Redirections are evaluated strictly from left to right, which is why cmd >log 2>&1 and cmd 2>&1 >log behave differently: in the latter case, errors continue printing to the terminal.

    First seen in: Key components · Processes and redirections

    Pipeline a | b #

    A chain of commands where the output of each process feeds directly into the input of the next.

    Pipeline stages execute concurrently in separate subshell processes rather than sequentially. By default, the overall exit status of the pipeline is that of the final command alone - causing failing_command | tee log to return 0. The complete array of return codes for all pipeline stages is preserved in ${PIPESTATUS[@]}.

    First seen in: Key components · Pipelines and exit statuses

    Exit status $? #

    A status byte from 0 to 255 signaling command success (0) or failure (non-zero).

    It is the sole machine-readable indicator of success or failure: stderr messages are meant for human operators, while exit codes are meant for automation. An error message unaccompanied by a non-zero exit code means CI registers a passing step. Codes 126, 127, and 128+N are issued directly by the shell: "permission denied/not executable", "command not found", and "terminated by signal N".

    First seen in: Key components · Pipelines and exit statuses

    Subshell ( ... ) #

    A child shell process that inherits the environment, but whose modifications never propagate back to the parent.

    Hence the classic pitfall: a loop consuming output from a pipe counts items, but once the loop terminates, the counter variable is empty again - the loop executed within an isolated subshell. Subshells are spawned by parentheses, pipeline stages, and $( ) command substitutions; curly braces do not create subshells. Understanding this boundary explains lost cd directory changes and exit calls that fail to terminate the enclosing script.

    First seen in: Key components · Variables and scopes

    Signal SIGINT · SIGTERM · SIGKILL #

    An asynchronous notification delivered to a process by the kernel, another process, or the controlling terminal.

    SIGINT is dispatched by Ctrl+C, SIGTERM by kill and container orchestrator stops, and SIGKILL by kill -9. Processes can trap the first two to perform graceful shutdown; SIGKILL cannot be trapped or ignored because it is handled directly by the kernel. A process terminated by signal N returns exit status 128+N: 130 for Ctrl+C, 143 for SIGTERM.

    First seen in: Key components · Signals and traps

    Trap trap … EXIT #

    An action registered with the shell to execute upon receiving an OS signal or internal runtime event.

    A trap on EXIT fires whenever the shell process terminates normally, on error, or via an interrupt, making it the only dependable mechanism for cleaning up temporary resources. The sole exception is SIGKILL: the kernel destroys the process immediately, bypassing user space traps entirely. Traps on ERR execute on command failure; ensuring they are inherited by shell functions and subshells requires set -E.

    First seen in: Key components · Signals and traps

    POSIX and bashisms #!/bin/sh #

    POSIX defines the baseline specification common across Unix shells; bashisms are features specific to Bash.

    Arrays, [[ ]] conditionals, process substitution, and ${v//a/b} parameter expansions are bashisms: they fail under dash, which is symlinked to /bin/sh on Debian and Ubuntu. Choose deliberately from the start: either use #!/usr/bin/env bash with full feature access, or choose #!/bin/sh, validate with shellcheck -s sh, and avoid non-standard syntax.

    First seen in: Weaknesses and limits · Portability

    Practice: scripts that survive production #

    Strict mode set -euo pipefail #

    Three safety fuses: abort on error, abort on unset variable, do not mask failures inside pipelines.

    -e exits on non-zero return codes, but is ignored inside conditions, &&, || lists, function calls in conditionals, and local x=$(cmd). -u treats uninitialized variables as fatal errors rather than silently substituting an empty string. -o pipefail propagates the exit status of the rightmost failing pipeline command. It establishes a necessary hygiene baseline, not an absolute guarantee of script safety.

    First seen in: Writing scripts · Skeleton

    Dry run --dry-run #

    An execution mode where the script prints planned mutations without executing them.

    It provides reliable guarantees only when engineered systematically: every state-mutating command routes through a single wrapper function that prints instead of executing when dry run is active. Retrofitted haphazardly, it inevitably misses dangerous branches. Furthermore, wrappers cannot prevent shell redirection side effects: run cmd > file truncates the target file even in dry-run mode because > is processed by the shell prior to function execution. For AI agents, dry run is the principal method for validating logic safely; for engineers, it enables review before changes take effect.

    First seen in: Examples · Pro · Options and --dry-run

    Idempotence mkdir -p · ln -sfn #

    A property of an operation: executing it repeatedly yields the same result without corrupting system state.

    In automated environments, retries are inevitable: network timeouts, node restarts, duplicate events, or an autonomous agent repeating steps. Commands like mkdir -p, ln -sfn, and rsync are idempotent; bare mkdir and unmanaged >> append operations are not. Non-idempotent operations require unique operation identifiers, running only when that identifier is absent from the execution ledger.

    First seen in: Writing scripts · Idempotence and cleanup

    Atomicity mv -T #

    A property of an operation: it completes entirely or has no effect, exposing no intermediate state to observers.

    Renaming a file on the same filesystem is atomic; copying is not. For this reason, output files should be generated in a temporary staging path and swapped into place with an atomic mv. Similarly, switching a symlink to a new release is done via ln -sfn to a temporary path followed by mv -T over the active link. The sequence of rm followed by ln -s is not atomic: between the two steps, no link exists.

    First seen in: DevOps practices · Deployment and rollback

    Locking flock #

    A concurrency guard ensuring that multiple instances of the same task never execute simultaneously.

    flock maintains an exclusive lock tied to an open file descriptor, which the operating system automatically releases when the process terminates - including on unexpected crashes. Primitive PID file-based locks lack this kernel protection: after an unhandled crash, stale lock files remain on disk, blocking subsequent runs indefinitely. Its standard application is a scheduled cron job that might overrun its execution window.

    First seen in: Examples · Pro · Single instance

    Decisions: bounding the worst case #

    Tool contract stdout · stderr · codes · --json #

    The public runtime contract of a script upon which calling automation and external systems rely.

    A script contract specifies stream conventions, valid exit codes, structured output formats, dry-run flags, and backward compatibility guarantees. Implementation logic may be refactored freely, but the public contract cannot: external systems depend on it, and unannounced changes break downstream consumers without warning. Custom exit codes should be selected from the 3-63 range or align with sysexits.h, leaving codes 126, 127, and 128+N reserved for shell and signal semantics.

    First seen in: Examples · IGL · Script contract

    Blast radius blast radius #

    The maximum potential damage a script can cause when it fails or encounters unexpected input.

    Robust scripts are engineered around the worst-case scenario rather than optimistic assumptions. Blast radius is constrained by two checks at the very start: an allowlist bounding the operational target (restricting execution to explicit directory paths or resource identifiers) and an upper limit on items modified per invocation. A script that resolves three thousand targets instead of five must abort immediately and alert a human: this transforms a catastrophic outage into an ordinary operational incident.
