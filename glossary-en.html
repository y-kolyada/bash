    Glossary

    Six words that the other pages will not stop to explain again. None of them is an exam definition — each is a mechanism whose absence costs an incident.

    The key idea of this glossary #

    This glossary exists to remove ambiguity rather than to be memorised: while “an error” and “a non-zero exit code” are two different things to you, arguing about a script's reliability is pointless. Each card has three layers: one sentence for recognition, a paragraph of mechanism, and a line saying where it first came up. The cards are deliberately short — density beats completeness, and the complete description is in man bash.

    Shebang #!/usr/bin/env bash #

    A script's first line, telling the kernel which interpreter to run it with.

    Without it the script runs in whichever shell invoked it — and on a machine where sh is dash, arrays and [[ ]] stop working. The env form looks for bash in PATH rather than only in /bin: on macOS and the BSDs it lives elsewhere.

    🎯 First seen in: Home · Toolchain

    Exit code $? #

    A number from 0 to 255 by which a command reports success (0) or failure (non-zero).

    It is the only machine-readable sign of failure: text on stderr is for humans, the exit code is for automation. Hence the rule: an error message without a non-zero code means CI sees green. ./check.sh is built on exactly this.

    🎯 First seen in: Home · Seven goals

    Pipeline a | b #

    A chain of commands where one's output becomes the next one's input.

    The stages start simultaneously, not in turn, and each lives in its own process. By default the pipeline's exit code is taken from the last stage only — so failing_command | tee log returns 0. The full set of codes is in ${PIPESTATUS[@]}.

    🎯 First seen in: Home · Three levels

    Strict mode set -euo pipefail #

    Three fuses: fail on error, fail on an unset variable, do not lose a failure inside a pipeline.

    -e exits on a non-zero code, but not inside conditions, && chains, or functions called in a condition. -u turns a typo in a variable name into a stop rather than an empty string. -o pipefail surfaces the code of the first failing stage. This is a hygiene minimum, not a guarantee of reliability.

    🎯 First seen in: Home · Three levels

    Word splitting "$var" #

    Splitting the result of an expansion into separate words on whitespace and newlines.

    Bash substitutes the variable's value and then cuts it up. So the path /home/My Files/a.txt becomes two arguments when unquoted, and a delete command deletes something other than what you meant. Quoting an expansion is not style but defence — and it is the first mistake AI agents make regularly.

    🎯 First seen in: Home · Seven goals

    Subshell ( ... ) #

    A child shell process: it inherits the environment, but its changes never come back out.

    Hence the classic puzzle: a loop after a pipe counts lines, and once it ends the variable is empty again — the loop ran in a subshell. Understanding the process boundary explains half of the “mysterious” breakage in scripts, including the cd that did not stick.
