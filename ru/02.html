    Написание скриптов

    Слов: 1004

    Правила и техники, которые отличают скрипт, работающий на вашей машине, от скрипта, работающего на чужой. И граница между двумя режимами Bash, из которой растёт половина багов.

    Главная мысль страницы #

    Скрипт отличается от набора команд не длиной, а тем, что его выполняют без вас. Человек за терминалом видит ошибку и останавливается; скрипт её проглатывает и идёт дальше, поэтому всё, что вы держали в голове, приходится написать явно: строгий режим, проверку аргументов, уборку за собой и честные коды возврата. Вторая половина этой страницы - про границу между интерактивной оболочкой и интерпретатором скрипта: это разные режимы одной программы, и они читают разные файлы настроек. Отсюда классическое «у меня в терминале работает, а в cron нет», и отсюда же правило: скрипт не должен зависеть от настроек вашей оболочки. Всё остальное на этой странице - следствия этих двух мыслей.

    1 · Два режима: оболочка и интерпретатор #

    Bash - одна программа с двумя разными ролями, и половина «необъяснимых» отличий между терминалом и скриптом объясняется именно этой границей. Интерактивная оболочка читает команды от человека: у неё есть история, автодополнение, приглашение, псевдонимы. Интерпретатор скрипта читает файл: ничего из перечисленного ему не нужно, и он этого не загружает.

    bash -c 'shopt -q login_shell; echo $?'
# 1 - не login-оболочка

echo $-            # в скрипте нет i
# hB  (интерактивная даст himBH)

    Отсюда три следствия, которые чаще всего и приносят баг. Псевдонимы в скрипте не работают - expand_aliases по умолчанию выключен для неинтерактивной оболочки. ~/.bashrc скрипт не читает: он читается только интерактивной не-login-оболочкой, поэтому ваш PATH из .bashrc в cron или в CI не появится. ~/.bash_profile читает только login - вход по ssh, su -, первая консоль.

    Практический вывод: скрипт не должен зависеть от настроек вашей оболочки. Всё, что ему нужно, он объявляет сам - путь, переменные, язык вывода.

    Что спрашивают: «Почему мой alias или PATH работает в терминале и не работает в скрипте или в cron?»

    2 · Скелет: одинаковое начало у любого скрипта #

    У хорошего скрипта первые пять строк всегда одни и те же, и их стоит набирать не думая - думать надо дальше.

    #!/usr/bin/env bash
set -euo pipefail
IFS=$'\n\t'

usage() { echo "usage: $0 <file>" >&2; exit 2; }
[ $# -eq 1 ] || usage

    env bash находит тот Bash, который есть у пользователя, а не только /bin/bash. set -euo pipefail - три предохранителя: падать на ошибке, падать на необъявленной переменной, не терять ошибку внутри конвейера. Сужение IFS до перевода строки и табуляции убирает разбиение по пробелам там, где оно почти никогда не нужно.

    Проверка аргументов - часть скелета, а не украшение. Скрипт, запущенный без параметров, должен сказать, чего он хочет, и выйти с ненулевым кодом, а не падать на пустой переменной в середине работы.

    Что спрашивают: «Что делает set -euo pipefail и чего он не делает?»

    3 · Функции и аргументы #

    Переменная внутри функции по умолчанию глобальная. Без local функция молча затирает чужое значение, и найти это потом трудно.

    greet() {
  local name="${1:?нужно имя}"
  printf 'привет, %s\n' "$name"
}

# результат - через stdout,
# статус - через код возврата
if out=$(greet "мир"); then
  echo "$out"
fi

    Два канала не путают: stdout - это результат, код возврата - это статус. Функция, которая печатает «ошибка» и возвращает 0, ломает любой вызывающий код.

    "${1:?сообщение}" - обязательный аргумент: если его нет, Bash сам остановит скрипт с понятным текстом. Для разбора ключей есть getopts; самодельный цикл с case оправдан только для длинных опций, которых getopts не умеет.

    Что спрашивают: «Чем отличается возврат значения из функции в Bash от return в других языках?»

    4 · Идемпотентность и уборка #

    Скрипт, который нельзя запустить дважды, - это полскрипта. В эксплуатации его запустят дважды обязательно: по ошибке, после таймаута, при повторе задачи в CI.

    tmp=$(mktemp -d)
trap 'rm -rf "$tmp"' EXIT

mkdir -p /opt/app/releases
ln -sfn "$new" /opt/app/current

    mkdir -p, ln -sfn, rsync, install -D - это команды, которым безразлично, был ли результат уже достигнут. mkdir без -p и ln -s без -f - нет.

    Ловушка на EXIT - единственная надёжная уборка: она срабатывает и при ошибке, и при Ctrl+C. Имя временного файла придумывает mktemp, а не вы: предсказуемое имя в /tmp - это и гонка, и дыра в безопасности.

    Что спрашивают: «Как сделать скрипт безопасным для повторного запуска и как гарантировать уборку временных файлов?»

    5 · Логирование и диагностика #

    Разделение потоков - не стиль, а условие работы в конвейере: результат идёт в stdout, всё остальное в stderr. Иначе ваш «[INFO] начинаю» попадёт в данные, которые читает следующая команда.

    log() { printf '%s %s\n' "$(date +%T)" "$*" >&2; }

log "начинаю"
PS4='+ ${BASH_SOURCE}:${LINENO}: '
set -x          # включить трассировку
set +x          # выключить

    set -x печатает каждую команду после подстановок - это самый быстрый способ увидеть, что реально выполняется. PS4 добавляет к трассировке файл и строку. Включать трассировку на всём скрипте в продакшне опасно: в неё попадут значения переменных, то есть и секреты.

    Что спрашивают: «Куда писать сообщения скрипта и почему не в stdout?»

    6 · Качество: shellcheck и формат #

    У Bash есть статический анализатор, и он находит почти все типовые ошибки раньше вас: незакавыченные подстановки, бесполезный cat, сравнение строк как чисел, cd без проверки.

    shellcheck script.sh
shfmt -i 2 -w script.sh

# в начале файла - осознанное
# отключение правила:
# shellcheck disable=SC2086

    Отключать правило можно, но только строкой выше и с комментарием, почему. Глобально выключенный SC2086 означает «мы решили не закавычивать подстановки», и это решение стоит принимать вслух.

    Для тестов есть bats. Но первый тест любого скрипта - запуск с --dry-run: режим, в котором он печатает, что сделал бы, и ничего не делает. Его стоит заложить сразу, а не после первого инцидента.

    Что спрашивают: «Чем вы проверяете shell-скрипты и что делает shellcheck такого, чего не видит человек?»

    Скелет, который набирается не думая, и понимание, почему именно такой. Время потрачено не зря, если вы перестали объяснять поломки словом «почему-то»: у каждой из них здесь названо место - режим оболочки, незакавыченная подстановка, потерянный код возврата или отсутствующая ловушка. Это и есть перестройка нейросети: скелет вы забудете набрать по памяти через месяц, а причину, по которой он такой, - нет.

    1. Граница двух режимов: что читает интерактивная оболочка, а что - скрипт.
    2. Скелет из пяти строк: shebang, строгий режим, IFS, usage, проверка аргументов.
    3. Правило двух каналов: stdout - результат, stderr - всё остальное, код возврата - статус.
    4. Идемпотентность и trap EXIT как требование, а не как аккуратность.
    5. shellcheck и --dry-run - две проверки, которые дешевле любого инцидента.
