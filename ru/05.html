    Взаимосвязи

    Где Bash стыкуется с Git, CI, Docker, systemd, Make и Ansible - и что в каждом из этих швов ломается чаще всего.

    Главная мысль страницы #

    Bash редко работает сам по себе: он живёт внутри чужих инструментов, и большинство проблем возникает не в нём, а на границе. Git-хук решает судьбу коммита кодом возврата. CI запускает ваш шаг с собственным набором ключей и новым процессом на каждый шаг. Docker в строчной форме ставит PID 1 оболочкой, и контейнер перестаёт останавливаться по сигналу. systemd разбирает ExecStart сам, без оболочки. Make и Ansible выполняют каждую строку в своей оболочке. Выучив шесть этих швов, вы закрываете основную часть вопросов на ассессменте - и большую часть реальных инцидентов.

    1 · Git: хуки и фильтры #

    Git не имеет собственного языка расширения - он запускает исполняемые файлы, и почти всегда это shell. Хук получает данные через аргументы или stdin, а решение принимает кодом возврата: ненулевой отменяет операцию.

    #!/usr/bin/env bash
# .git/hooks/pre-commit
set -euo pipefail

files=$(git diff --cached --name-only \
        --diff-filter=ACM | grep '\.sh$' || true)
[ -z "$files" ] && exit 0
shellcheck $files

    Две ловушки. Первая: grep без совпадений возвращает 1 и под set -e уронит хук - отсюда || true. Вторая: хуки не хранятся в репозитории, папка .git/hooks не версионируется; поэтому хуки кладут в отдельный каталог и включают через git config core.hooksPath, иначе у коллег их просто не будет.

    Что спрашивают: «Как заставить хук отменить коммит и почему хуки не попадают к другим разработчикам сами?»

    2 · CI и GitHub Actions: shell по умолчанию #

    Шаг run: - это shell-скрипт, который CI пишет во временный файл и запускает. Важно знать, с какими ключами, и здесь есть тонкость, о которую спотыкаются: если shell: не указан, GitHub Actions запускает bash -e {0} - set -e есть, pipefail нет. Если указать shell: bash явно, запуск становится bash --noprofile --norc -eo pipefail {0} - pipefail появляется. -u нет ни в одном варианте.

    - name: build
  shell: bash          # даёт -eo pipefail
  run: |
    set -euo pipefail  # -u всё равно свой
    ./build.sh

# каждый шаг - новый процесс:
# export в одном шаге не виден
# в следующем
echo "VER=1.2" >> "$GITHUB_ENV"

    Каждый шаг - отдельный процесс, поэтому переменные между шагами передаются через файлы ($GITHUB_ENV, $GITHUB_OUTPUT), а не через export. И отдельная осторожность: set -x в шаге печатает значения переменных, то есть выводит секреты в журнал - маскирование спасает не всегда.

    Что спрашивают: «С какими ключами CI запускает ваш run: и как передать значение между шагами?»

    3 · Docker: PID 1, сигналы и форма записи #

    Самая частая ошибка в ENTRYPOINT не про shell, а про процессы. В строчной форме команда запускается через /bin/sh -c, и PID 1 получает оболочка, а не ваше приложение - сигнал SIGTERM до него не дойдёт, и остановка контейнера превратится в убийство по таймауту.

    # плохо: PID 1 - это sh
ENTRYPOINT /app/run.sh

# хорошо: exec-форма
ENTRYPOINT ["/app/run.sh"]

# и в самом скрипте, в конце:
exec /app/server "$@"

    exec заменяет процесс оболочки процессом приложения - PID 1 становится приложением, сигналы доходят. В контейнере нет init, поэтому зомби-процессы никто не собирает; если ваш скрипт порождает фоновые задачи, нужен --init или tini. И помните про Alpine: там /bin/sh - это busybox ash, и bash отсутствует вовсе.

    Что спрашивают: «Почему контейнер не останавливается по docker stop и причём тут форма записи ENTRYPOINT?»

    4 · systemd: когда скрипт не нужен #

    systemd умеет многое из того, ради чего пишут скрипты-обёртки: перезапуск, зависимости, ограничение ресурсов, журнал. Обёртка, которая только запускает и перезапускает, лишняя.

    [Service]
ExecStart=/usr/bin/app --port 8080
Restart=on-failure
EnvironmentFile=/etc/app.env

# ExecStart - не shell:
# ни $VAR, ни | , ни > тут нет
ExecStart=/bin/bash -c 'app | tee -a log'
# так - только если без этого никак

    Строка ExecStart разбирается самим systemd, а не оболочкой: подстановки, конвейеры и перенаправления там не работают. Если они действительно нужны - вызов bash -c явный и осознанный. Логи пишутся в stdout/stderr и попадают в journalctl; самодельная ротация файлов в скрипте - почти всегда лишняя работа.

    Что спрашивают: «Почему в ExecStart не работает перенаправление и когда нужен bash -c?»

    5 · Make и Ansible: каждая строка - своя оболочка #

    Общая ошибка обоих инструментов: строки не продолжают друг друга. В Make каждая строка рецепта исполняется в отдельной оболочке, поэтому cd из первой строки во второй уже не действует.

    # не работает:
build:
	cd src
	make all

# работает:
build:
	cd src && make all

# или один shell на весь рецепт:
.ONESHELL:

    В Ansible то же самое: модуль shell запускает строку заново для каждой задачи. И там ещё одно различие, которое спрашивают: command запускает программу напрямую, без оболочки - без конвейеров, подстановок и шаблонов имён; shell - через оболочку, со всеми возможностями и всеми рисками. Правило: command, пока не доказано, что нужен shell.

    Что спрашивают: «Почему cd в Makefile не действует на следующую строку и чем command отличается от shell в Ansible?»

    6 · Где Bash заканчивается: jq, awk, Python #

    Соседи по экосистеме делят работу по типу данных, и знание границы экономит часы.

    # структура - jq
jq -r '.items[] | select(.ok).id' f.json

# колонки и арифметика - awk
awk -F, '{s+=$3} END{print s/NR}' f.csv

# всё остальное - язык
python3 -c 'import json, sys; ...'

    jq - для всего, что имеет вложенность. awk - для построчных данных с колонками и подсчётами; он же часто заменяет связку grep | cut | sort одной командой и одним процессом. Python - когда нужны библиотеки, сеть сложнее curl, или состояние между шагами.

    Практический признак: как только в скрипте появился второй jq с собственным выражением на три строки - задача уже не про Bash.

    Что спрашивают: «Когда вы берёте awk вместо связки grep | cut и когда уходите в Python?»

    Артефакты: что у вас есть после этой страницы #

    Чтение >> Ваш квант времени жизни · Партнёрство достоинства вместе с AI · Перестройка вашей нейросети

    Карта швов вместо набора рецептов. Время потрачено не зря, если вы теперь спрашиваете про чужой инструмент правильное: кто здесь запускает мою строку, в каком процессе и что он сделает с кодом возврата. Это и есть перестройка нейросети: вопрос «почему не работает» заменяется вопросом «кто это выполняет».

    1. Git: решение - кодом возврата; хуки не версионируются без core.hooksPath.
    2. CI: без shell: - bash -e, с shell: bash - ещё и pipefail; -u нет нигде; переменные между шагами - через файлы.
    3. Docker: exec-форма, exec в конце скрипта, отсутствие init.
    4. systemd: ExecStart - не оболочка; логи в журнал, а не в файл.
    5. Make и Ansible: каждая строка в своей оболочке; command против shell.
    6. Граница с jq, awk и Python по типу данных, а не по привычке.
