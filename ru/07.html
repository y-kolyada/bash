    Практики в Clouds

    CLI облака, ожидание готовности, доступы без ключей, лимиты API, защита от чужого аккаунта и уборка по тегам - и где проходит граница с Terraform.

    Главная мысль страницы #

    В облаке Bash управляет вызовами чужого API, где каждый запрос стоит времени, квоты и денег. Качество облачного скрипта определяют четыре правила: он ждёт готовности асинхронных ресурсов явно и с пределом попыток; никогда не хранит ключи в коде и не светит их под set -x; запрашивает данные пачками с учётом пагинации и лимитов API вместо сотен вызовов в цикле; и на первой же строке проверяет, в какой аккаунт и регион он смотрит. Всё, что скрипт создал для задачи, он обязан уметь найти и удалить по тегу. А архитектурная граница простая: одноразовое действие - это Bash, постоянное состояние инфраструктуры - это Terraform. Триаж самой живой машины и её логов вынесен в отдельный раздел практик SRE.

    1 · CLI облака - обычная программа, и ведёт себя как программа #

    Первое, что меняет отношение к облачному CLI: это не консоль администратора, а утилита с кодом возврата и машинным выводом. Значит, к ней применимы те же правила, что к grep.

    aws ec2 describe-instances \
  --filters Name=tag:app,Values=web \
  --query 'Reservations[].Instances[].InstanceId' \
  --output text

aws s3api head-object … >/dev/null 2>&1 \
  && echo есть || echo нет

    Два приёма экономят больше всего времени. --query фильтрует на стороне CLI, до того как данные дойдут до jq: меньше текста, меньше разбора. Отсутствие объекта - это ненулевой код возврата, а не пустая строка; проверять надо код, а не вывод. И отключайте встроенный пейджер через AWS_PAGER="", чтобы скрипт не завис в ожидании клавиши q.

    Что спрашивают: «Чем --query отличается от jq и как в скрипте проверить, существует ли ресурс?»

    2 · Создание ресурсов: ожидание - часть работы #

    Облачные вызовы асинхронны: команда вернула идентификатор - это не значит, что ресурс готов. Скрипт, который не ждёт, падает через раз и выглядит как «плавающая ошибка».

    id=$(aws ec2 run-instances … \
     --query 'Instances[0].InstanceId' \
     --output text)

aws ec2 wait instance-running \
  --instance-ids "$id"

# своё ожидание - с пределом
for i in {1..30}; do
  ready && break
  sleep 5
done

    У CLI есть встроенные ожидания (wait) - берите их. Там, где их нет, пишите цикл с обязательным пределом попыток: бесконечное ожидание в CI означает, что задача висит до таймаута и жрёт минуты. И помечайте всё, что создаёте, тегами - по ним вы потом это найдёте и удалите.

    Что спрашивают: «Как в скрипте дождаться готовности облачного ресурса и что будет без ожидания?»

    3 · Доступы: чего в скрипте быть не должно #

    Самая дорогая ошибка в облачных скриптах не техническая, а дисциплинарная - ключ, попавший в репозиторий или в журнал.

    # нет:
AWS_SECRET_ACCESS_KEY=AKIA…

# да: роль инстанса или профиль
aws --profile prod s3 ls

# секрет - из хранилища, в переменную,
# и никогда в echo и не под set -x
token=$(aws secretsmanager \
  get-secret-value --secret-id t \
  --query SecretString --output text)

    Порядок предпочтения: роль инстанса или OIDC - ничего хранить не нужно; профиль - ключи лежат у пользователя, а не в коде; переменные окружения - только как последнее средство. Отдельно: set -x печатает значения, то есть выводит секрет в журнал CI; включать трассировку в шаге, который работает с секретами, нельзя.

    Что спрашивают: «Как скрипт получает доступ к облаку без хранения ключей и почему set -x там опасен?»

    4 · Пагинация, троттлинг API и запрет на вызовы в цикле #

    Вызов облачного CLI в цикле for по сотне ресурсов - верный способ упереться в ThrottlingException (Rate exceeded) и растянуть скрипт на полчаса: каждый вызов поднимает Python/Go-рантайм и открывает новую TLS-сессию.

    # нет: N вызовов API в цикле
for id in $ids; do
  aws ec2 describe-instances --instance-ids "$id"
done

# да: один пакетный запрос и адаптивный retry
export AWS_RETRY_MODE=adaptive
export AWS_MAX_ATTEMPTS=6
aws ec2 describe-instances \
  --instance-ids $ids

    Два правила для больших облаков: передавать идентификаторы пачкой или фильтром на стороне API вместо поштучного перебора, и включать встроенный адаптивный режим повторов (AWS_RETRY_MODE=adaptive), который сам снижает частоту запросов при ответе 429/503. А при чтении больших списков помнить, что без автопагинации или --next-token вернётся только первая страница.

    Что спрашивают: «Почему облачный скрипт внезапно падает с ошибкой Rate Exceeded и как избавиться от вызовов CLI в цикле?»

    5 · Защита от не того аккаунта, региона и контекста #

    Самая разрушительная авария в облаке происходит, когда правильный скрипт очистки запускают в терминале, где со вчерашнего дня остался профиль или контекст продакшна.

    #!/usr/bin/env bash
set -euo pipefail

export AWS_PAGER=""
region="${AWS_REGION:?укажите регион}"
want_acc="123456789012"

got_acc=$(aws sts get-caller-identity \
  --query Account --output text)
[ "$got_acc" = "$want_acc" ] || {
  echo "чужой аккаунт: $got_acc" >&2
  exit 1
}

    Любой скрипт, который изменяет или удаляет облачные ресурсы, обязан в первых строках сверить фактический аккаунт и кластер с ожидаемым (aws sts get-caller-identity, gcloud config get-value project, kubectl config current-context) и требовать явного указания региона, не полагаясь на переменные, случайно унаследованные из интерактивной оболочки инженера.

    Что спрашивают: «Как гарантировать, что скрипт для тестового облака случайно не удалит ресурсы в продакшне?»

    6 · Уборка и граница с Terraform #

    Облако берёт деньги за забытое. Скрипт, который создаёт, обязан уметь удалять - и находить то, что нужно удалить, по тегам, а не по списку в голове.

    aws ec2 describe-instances \
  --filters Name=tag:tmp,Values=yes \
  --query '…[].InstanceId' --output text \
  | xargs -r aws ec2 terminate-instances \
      --instance-ids

    xargs -r не запустит команду на пустом вводе - без него удаление «всего» может превратиться в команду без аргументов с непредсказуемым поведением.

    Где проходит граница. Bash хорош там, где задача про действие: создать на час, собрать срез по аккаунту, мигрировать бакет, удалить по тегу. Terraform и CloudFormation - там, где задача про состояние: что должно существовать постоянно. Скрипт, который пытается поддерживать состояние, неизбежно превращается в плохой Terraform - со своим файлом состояния, своей проверкой расхождений и своими ошибками.

    Что спрашивают: «Где заканчивается скрипт провижининга и начинается Terraform?»

    Проверка аккаунта на входе и уборка по тегу на выходе. Время потрачено не зря, если вы перестали вызывать облачный CLI в цикле по одному ресурсу и начинаете каждый скрипт со сверки идентификатора аккаунта, а создание каждого временного ресурса - с тега. Это и есть перестройка нейросети: облако перестаёт быть местом случайных счетов и чужих регионов.

    1. CLI как программа: код возврата, --query на стороне клиента, отключение AWS_PAGER.
    2. Явное ожидание готовности через wait или цикл с пределом попыток.
    3. Порядок доступов: роль или OIDC → профиль → переменная; запрет на set -x с секретами.
    4. Пакетные запросы и AWS_RETRY_MODE=adaptive вместо вызовов CLI в цикле.
    5. Проверка аккаунта и региона в первой строке скрипта до любых изменений.
    6. Уборка по тегам, xargs -r и граница: действие - Bash, состояние - Terraform.
