    Практики DevOps

    Bash в конвейере поставки: сборка, среды, деплой и откат, проверки до слияния и работа с секретами. И признаки, по которым видно, что конвейер перерос скрипт.

    Главная мысль страницы #

    В конвейере поставки Bash встречается чаще всего и ошибок там дороже всего, потому что шаг CI - это ваш скрипт, запущенный чужим способом: с чужими ключами, в новом процессе и в сброшенном каталоге. Отсюда первое правило - шаг должен быть самодостаточным, а длинная логика жить в файле репозитория, который можно запустить локально. Второе правило про сборку: версия берётся из системы контроля, а latest версией не является, потому что по нему нельзя откатиться. Третье - один скрипт на все среды с обязательным аргументом, потому что умолчание рано или поздно задеплоит в прод. И четвёртое, самое спрашиваемое на собеседованиях: откат проектируют раньше деплоя.

    1 · Bash в конвейере: чей это процесс #

    Шаг CI - это ваш скрипт, запущенный чужим способом. Три факта об этом запуске определяют почти всё поведение.

    # 1. ключи задаёт CI, не вы
#    без shell: -> bash -e
#    shell: bash -> + pipefail
set -euo pipefail   # -u - только свой

# 2. каждый шаг - новый процесс
echo "VER=$v" >> "$GITHUB_ENV"

# 3. рабочий каталог сбрасывается
cd "$GITHUB_WORKSPACE"

    Отсюда правило: шаг должен быть самодостаточным. Он не полагается на export из предыдущего шага, не рассчитывает на текущий каталог и объявляет свой строгий режим сам. Длинную логику выносят в файл .sh в репозитории: его можно запустить локально, проверить shellcheck и прочитать в diff - в отличие от двадцати строк внутри YAML.

    Что спрашивают: «Почему переменная из одного шага CI не видна в следующем и как её передать?»

    2 · Сборка: воспроизводимость важнее скорости #

    Скрипт сборки отвечает на один вопрос: получится ли завтра то же самое, что сегодня. Всё остальное вторично.

    ver=$(git describe --tags --always --dirty)
sha=$(git rev-parse --short HEAD)

docker build \
  --build-arg VER="$ver" \
  -t "app:$sha" .

# артефакт называется версией,
# а не latest

    Три правила, которые ловят большинство проблем. Версия берётся из системы контроля, а не из переменной - её нельзя забыть обновить. latest не является версией: по нему невозможно откатиться. Суффикс --dirty показывает, что собрано из незакоммиченного дерева - это тот случай, когда артефакт воспроизвести уже нельзя, и об этом лучше знать сразу.

    Что спрашивают: «Откуда берётся номер версии артефакта и почему нельзя деплоить latest?»

    3 · Среды Dev → QA → Prod: один скрипт, разные параметры #

    Типичная ошибка - три похожих скрипта по одному на среду. Через месяц они расходятся, и деплой в прод делает не то, что проверяли на QA.

    #!/usr/bin/env bash
set -euo pipefail
env="${1:?dev|qa|prod}"
cfg="deploy/$env.env"
[ -f "$cfg" ] || { echo "нет $cfg" >&2; exit 2; }
# shellcheck source=/dev/null
source "$cfg"

[ "$env" = prod ] && : "${APPROVED:?нужно подтверждение}"

    Один скрипт, конфигурация снаружи, среда - обязательный аргумент. Никаких значений по умолчанию для среды: скрипт, который без аргумента деплоит в прод, рано или поздно задеплоит в прод. Дополнительный гейт для продакшна делается явной переменной, а не комментарием в начале файла.

    Что спрашивают: «Как один скрипт обслуживает три среды и как вы защищаете прод от случайного запуска?»

    4 · Деплой и откат: откат проектируют первым #

    Вопрос, который задают на собеседовании чаще, чем про сам деплой: как вы вернётесь назад. Если ответ требует новой сборки - ответ плохой.

    # релизы рядом, текущий - ссылка
ln -sfn "/opt/app/rel/$ver" /opt/app/next
mv -T /opt/app/next /opt/app/current
systemctl reload app

# откат = тот же шаг с прошлой версией

    ln -sfn плюс mv -T дают атомарную замену: в любой момент времени ссылка указывает либо на старый релиз, либо на новый, промежуточного состояния нет. Простая запись rm symlink && ln -s такого свойства не имеет - между двумя командами ссылки не существует вовсе.

    Проверка после деплоя - тоже часть скрипта: обращение к /health с пределом попыток и автоматический возврат на прошлую версию, если ответа нет.

    Что спрашивают: «Как сделать переключение версии атомарным и как устроен откат?»

    5 · Качество конвейера: проверки до слияния #

    Проверка скриптов - такой же шаг CI, как тесты приложения. Стоит он секунды, а ловит то, что иначе найдётся в проде.

    - run: |
    shopt -s globstar
    shellcheck **/*.sh
- run: shfmt -d -i 2 .
- run: bats tests/

    Тот же набор ставят локально через pre-commit, чтобы красное не доезжало до CI. Важно, чтобы локальная проверка и проверка в CI были одной и той же командой - иначе появляется класс ошибок «у меня проходит, в CI падает», и доверие к проверке теряется.

    Что спрашивают: «Какие проверки shell-кода вы ставите в конвейер и почему они должны совпадать с локальными?»

    6 · Секреты и журналы #

    Журнал CI - публичный для всех, у кого есть доступ к репозиторию, и он хранится дольше, чем помнят про секрет.

    # нет:
set -x               # напечатает всё
echo "token=$TOKEN"
curl -u "u:$PASS" …  # видно в ps

# да:
curl --netrc-file "$f" …
printf '%s' "$TOKEN" | cmd --token-stdin

    Три правила. Секрет не передаётся аргументом - аргументы видны в ps всем пользователям машины; его передают через stdin, файл или переменную окружения. Трассировка не включается в шагах с секретами. Маскирование CI - не гарантия: оно подменяет точное совпадение, и секрет, попавший в журнал по частям или в другой кодировке, в маску не попадёт.

    Что спрашивают: «Почему нельзя передавать пароль аргументом команды и что делает маскирование секретов в CI?»

    7 · Когда конвейер перерос скрипт #

    Признаки, что логику пора выносить из shell:

    • в скрипте появилось состояние, которое надо помнить между запусками;
    • шаги зависят друг от друга нелинейно - это задача для Make или графа CI, а не для последовательности;
    • одна и та же логика скопирована в три конвейера;
    • для понимания скрипта нужно знать, какие переменные выставляет CI.

    Первое лечится инструментом состояния, второе - графом зависимостей, третье - общим скриптом в репозитории или своим действием CI, четвёртое - переносом логики в файл, который запускается локально теми же командами.

    И обратное: конвейер из пятнадцати строк на Bash, который делают понятным три комментария, не нужно превращать в плагин. Сложность инструмента оправдывается размером задачи, а не её важностью.

    Артефакты: что у вас есть после этой страницы #

    Чтение >> Ваш квант времени жизни · Партнёрство достоинства вместе с AI · Перестройка вашей нейросети

    Понимание, что шаг CI - это чужой запуск вашего кода. Время потрачено не зря, если вы перестали удивляться тому, что в CI ведёт себя иначе, и начали спрашивать: с какими ключами запущено, в каком процессе, что с рабочим каталогом. Это и есть перестройка нейросети: конвейер перестаёт быть чёрным ящиком и становится местом, где выполняются ваши же команды.

    1. Три факта о шаге CI: чужие ключи, новый процесс, сброшенный каталог.
    2. Версия из Git и запрет на latest в деплое.
    3. Один скрипт на три среды с обязательным аргументом и гейтом для прода.
    4. Атомарное переключение через ln -sfn и mv -T, откат тем же шагом.
    5. Проверки до слияния, совпадающие с локальными.
    6. Правила секретов: не аргументом, без трассировки, маскирование не гарантия.
    7. Признаки, что конвейер перерос скрипт, и чем каждый из них лечится.
