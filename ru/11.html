    Примеры · Pro

    Семь приёмов для уровня «мои скрипты работают на чужих машинах». Задача уровня - убрать молчаливые отказы: всё, что может пойти не так, должно сказать об этом вслух.

    Главная мысль страницы #

    Разница между уровнями Noob и Pro не в знании команд, а в отношении к отказу. Новичок пишет сценарий удачного исхода; профессионал исходит из того, что команда упадёт, сеть моргнёт, скрипт запустят дважды и прервут на середине. Семь приёмов ниже закрывают именно это: громкое падение с номером строки, гарантированная уборка, режим проверки без последствий, повтор с пределом, параллельность со сбором отказов, защита от повторного запуска и журнал, не мешающий результату. Ни один из них не сложен. Сложно другое - вспомнить про них до инцидента, а не после.

    1 · Падать громко: trap ERR с номером строки #

    Задача: сделать так, чтобы отказ скрипта сам сообщал, где он произошёл.

    #!/usr/bin/env bash
set -Eeuo pipefail

on_err() {
  local rc=$?
  echo "ОТКАЗ: строка $1, код $rc" >&2
  exit "$rc"
}
trap 'on_err $LINENO' ERR
    Почему так: У Bash нет стека вызовов при падении, и строка отказа - единственное, что заменяет трассировку. Ключ -E обязателен: без него ловушка ERR не наследуется функциями и подоболочками, и отказ внутри функции пройдёт мимо обработчика. local rc=$? берётся первой строкой - любая следующая команда затрёт код возврата.

    2 · Временный каталог, который гарантированно уберётся #

    Задача: работать с промежуточными файлами и не оставить мусора ни при ошибке, ни при Ctrl+C.

    tmp=$(mktemp -d "${TMPDIR:-/tmp}/app.XXXXXX")
cleanup() { rm -rf "$tmp"; }
trap cleanup EXIT INT TERM

work > "$tmp/out"
mv "$tmp/out" result.txt
    Почему так: Ловушка на EXIT срабатывает при любом завершении, включая отказ под set -e, - кроме SIGKILL: его ядро не даёт перехватить. INT и TERM добавляют реакцию на прерывание и остановку. Имя придумывает mktemp, а не вы: предсказуемое имя в общем /tmp - это и гонка при параллельных запусках, и возможность подмены. Готовый результат переносится в целевое место одной командой - чтобы не было полуготового файла.

    3 · Опции и обязательный --dry-run #

    Задача: дать скрипту ключи и режим «показать, но не делать».

    dry=0; verbose=0
while getopts ":nvh" opt; do
  case $opt in
    n) dry=1 ;;
    v) verbose=1 ;;
    h) usage; exit 0 ;;
    \?) echo "неизвестный ключ" >&2; exit 2 ;;
  esac
done
shift $((OPTIND - 1))

run() { (( dry )) && { echo "DRY: $*"; return 0; }; "$@"; }
run rm -rf "$target"
    Почему так: Двоеточие в начале строки ключей переводит getopts в тихий режим - ошибки обрабатываете вы, а не он. shift $((OPTIND - 1)) убирает разобранные ключи, после чего $1 - первый позиционный аргумент. Обёртка run делает режим проверки структурным, а не добавленным потом: любая опасная команда проходит через неё, и забыть про --dry-run становится труднее, чем помнить. Одна оговорка, без которой обёртка опасна: перенаправления оболочка выполняет до входа в функцию. run echo x > file затрёт file и в режиме проверки, потому что > уже сработал. Всё, что пишет в файл, уводят внутрь вызова: run sh -c 'echo x > file' или отдельная функция записи, которая сама проверяет режим.

    4 · Повтор с нарастающей задержкой #

    Задача: пережить временный отказ сети, не превратив скрипт в вечный цикл.

    retry() {
  local n=0 max=5 delay=1
  until "$@"; do
    n=$((n + 1))
    (( n >= max )) && return 1
    sleep "$delay"
    delay=$((delay * 2))
  done
}

retry curl -fsS --max-time 10 "$url"
    Почему так: Три условия отделяют повтор от зацикливания: предел попыток, растущая задержка и таймаут у самой команды. Без --max-time повтор не поможет - первая же попытка повиснет навсегда. Ключ -f у curl обязателен: без него HTTP-ответ 500 считается успехом, и повторять будет нечего.

    5 · Параллельная обработка с ограничением и сбором отказов #

    Задача: обработать сотню файлов в четыре потока и узнать, упал ли хоть один.

    export -f process          # видимость в xargs

printf '%s\0' logs/*.log \
  | xargs -0 -P4 -I{} bash -c 'process "$@"' _ {} \
  || echo "часть задач упала" >&2

# своими руками - с учётом кодов:
pids=(); for f in …; do work "$f" & pids+=($!); done
rc=0; for p in "${pids[@]}"; do wait "$p" || rc=1; done
    Почему так: Разделитель \0 и ключ -0 делают конвейер устойчивым к пробелам и переводам строк в именах. xargs возвращает ненулевой код, если упала хотя бы одна задача - это и есть сбор отказов, которого нет у простого & плюс wait. Если коды нужны поимённо, сохраняйте $! и ждите каждый процесс отдельно.

    6 · Один экземпляр: защита от повторного запуска #

    Задача: не дать скрипту из cron запуститься второй раз, если предыдущий ещё работает.

    exec 9>/var/lock/app.lock
flock -n 9 || { echo "уже работает" >&2; exit 0; }

# дальше - обычная работа
    Почему так: Блокировка живёт на открытом дескрипторе, а не на файле: она снимается сама, когда процесс завершается - в том числе при аварийном завершении. Самодельный «файл-флаг» этим свойством не обладает: после падения он остаётся на диске и блокирует запуски навсегда. Ключ -n означает «не ждать»; выход с кодом 0 здесь осознанный - для cron это не ошибка, а нормальная ситуация.

    7 · Логирование с уровнями #

    Задача: дать скрипту голос, который не мешает его результату.

    LOG_LEVEL="${LOG_LEVEL:-info}"
_log() {
  local lvl=$1; shift
  printf '%s [%s] %s\n' \
    "$(date -Is)" "$lvl" "$*" >&2
}
info() { [ "$LOG_LEVEL" = debug ] || [ "$LOG_LEVEL" = info ] && _log INFO "$@"; }
die()  { _log ERROR "$@"; exit 1; }
    Почему так: Весь журнал идёт в stderr, потому что stdout - это результат, который может читать следующая команда в конвейере. Время в формате -Is (ISO 8601) сортируется как текст и однозначно разбирается машиной. Уровень берётся из переменной окружения: так включить подробность можно, не меняя скрипт, - это важно, когда он уже в продакшне.

    Семь готовых блоков и понимание, от чего защищает каждый. Время потрачено не зря, если при написании следующего скрипта вы ловите себя на вопросе «а что здесь произойдёт при отказе на середине» - и знаете, чем на него ответить. Это и есть перестройка нейросети: сценарий отказа перестаёт быть неприятной мыслью и становится частью проектирования.

    1. set -Eeuo pipefail и trap ERR $LINENO - отказ называет своё место.
    2. mktemp -d плюс trap EXIT INT TERM - уборка при любом исходе, кроме kill -9.
    3. getopts и обёртка run - режим проверки как структура, и перенаправления внутри вызова, а не снаружи.
    4. Повтор с пределом и таймаутом, и почему curl -f обязателен.
    5. xargs -0 -P - параллельность с устойчивыми именами и честным кодом.
    6. flock на дескрипторе, а не файл-флаг.
    7. Журнал в stderr с уровнем из окружения.
