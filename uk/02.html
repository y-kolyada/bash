    Написання скриптів

    Правила та техніки, які відрізняють скрипт, що працює на вашій машині, від скрипта, що працює на чужій. І межа між двома режимами Bash, з якої росте половина багів.

    Головна думка сторінки #

    Скрипт відрізняється від набору команд не довжиною, а тим, що його виконують без вас. Людина за терміналом бачить помилку і зупиняється; скрипт її ковтає і йде далі, тому все, що ви тримали в голові, доводиться написати явно: суворий режим, перевірку аргументів, прибирання за собою та чесні коди повернення. Друга половина цієї сторінки - про межу між інтерактивною оболонкою та інтерпретатором скрипту: це різні режими однієї програми, і вони читають різні файли налаштувань. Звідси класичне «у мене в терміналі працює, а в cron ні», і звідси ж правило: скрипт не повинен залежати від налаштувань вашої оболонки. Все інше на цій сторінці - наслідки цих двох думок.

    1 · Два режими: оболонка та інтерпретатор #

    Bash - одна програма з двома різними ролями, і половина «непояснюваних» відмінностей між терміналом і скриптом пояснюється саме цією межею. Інтерактивна оболонка читає команди від людини: у неї є історія, автодоповнення, запрошення, псевдоніми. Інтерпретатор скрипту читає файл: нічого з переліченого йому не потрібно, і він цього не завантажує.

    bash -c 'shopt -q login_shell; echo $?'
# 1 - не login-оболонка

echo $-            # у скрипті немає i
# hB  (інтерактивна дасть himBH)

    Звідси три наслідки, які найчастіше і приносять баг. Псевдоніми у скрипті не працюють - expand_aliases за замовчуванням вимкнений для неінтерактивної оболонки. ~/.bashrc скрипт не читає: він читається лише інтерактивною не-login-оболонкою, тому ваш PATH з .bashrc у cron або в CI не з'явиться. ~/.bash_profile читає лише login - вхід через ssh, su -, перша консоль.

    Практичний висновок: скрипт не повинен залежати від налаштувань вашої оболонки. Усе, що йому потрібно, він оголошує сам - шлях, змінні, мову виводу.

    Що запитують: «Чому мій alias або PATH працює в терміналі і не працює у скрипті чи в cron?»

    2 · Скелет: однаковий початок у будь-якого скрипту #

    У хорошого скрипту перші п'ять рядків завжди одні й ті самі, і їх варто набирати не думаючи - думати треба далі.

    #!/usr/bin/env bash
set -euo pipefail
IFS=$'\n\t'

usage() { echo "usage: $0 <file>" >&2; exit 2; }
[ $# -eq 1 ] || usage

    env bash знаходить той Bash, який є у користувача, а не лише /bin/bash. set -euo pipefail - три запобіжники: падати на помилці, падати на неоголошеній змінній, не втрачати помилку всередині конвеєра. Звуження IFS до переведення рядка і табуляції прибирає розбиття за пробілами там, де воно майже ніколи не потрібне.

    Перевірка аргументів - частина скелета, а не прикраса. Скрипт, запущений без параметрів, повинен сказати, чого він хоче, і вийти з ненульовим кодом, а не падати на порожній змінній у середині роботи.

    Що запитують: «Що робить set -euo pipefail і чого він не робить?»

    3 · Функції та аргументи #

    Змінна всередині функції за замовчуванням глобальна. Без local функція мовчки затирає чуже значення, і знайти це потім важко.

    greet() {
  local name="${1:?потрібне ім’я}"
  printf 'привіт, %s\n' "$name"
}

# результат - через stdout,
# статус - через код повернення
if out=$(greet "світ"); then
  echo "$out"
fi

    Два канали не плутають: stdout - це результат, код повернення - це статус. Функція, яка друкує «помилка» і повертає 0, ламає будь-який викликаючий код.

    "${1:?повідомлення}" - обов'язковий аргумент: якщо його немає, Bash сам зупинить скрипт зі зрозумілим текстом. Для розбору ключів є getopts; саморобний цикл із case виправданий лише для довгих опцій, яких getopts не вміє.

    Що запитують: «Чим відрізняється повернення значення з функції в Bash від return в інших мовах?»

    4 · Ідемпотентність і прибирання #

    Скрипт, який не можна запустити двічі, - це півскрипта. В експлуатації його запустять двічі обов'язково: помилково, після таймауту, при повторі завдання в CI.

    tmp=$(mktemp -d)
trap 'rm -rf "$tmp"' EXIT

mkdir -p /opt/app/releases
ln -sfn "$new" /opt/app/current

    mkdir -p, ln -sfn, rsync, install -D - це команди, яким байдуже, чи було результат вже досягнуто. mkdir без -p та ln -s без -f - ні.

    Пастка на EXIT - єдине надійне прибирання: вона спрацьовує і при помилці, і при Ctrl+C. Ім'я тимчасового файлу вигадує mktemp, а не ви: передбачуване ім'я в /tmp - це і стан гонки, і діра в безпеці.

    Що запитують: «Як зробити скрипт безпечним для повторного запуску і як гарантувати прибирання тимчасових файлів?»

    5 · Логування та діагностика #

    Розділення потоків - не стиль, а умова роботи в конвеєрі: результат іде в stdout, все інше в stderr. Інакше ваш «[INFO] починаю» потрапить у дані, які читає наступна команда.

    log() { printf '%s %s\n' "$(date +%T)" "$*" >&2; }

log "починаю"
PS4='+ ${BASH_SOURCE}:${LINENO}: '
set -x          # увімкнути трасування
set +x          # вимкнути

    set -x друкує кожну команду після підстановок - це найшвидший спосіб побачити, що реально виконується. PS4 додає до трасування файл і рядок. Вмикати трасування на всьому скрипті в продакшені небезпечно: до нього потраплять значення змінних, тобто і секрети.

    Що запитують: «Куди писати повідомлення скрипту і чому не в stdout?»

    6 · Якість: shellcheck та формат #

    У Bash є статичний аналізатор, і він знаходить майже всі типові помилки раніше за вас: незакавичковані підстановки, непотрібний cat, порівняння рядків як чисел, cd без перевірки.

    shellcheck script.sh
shfmt -i 2 -w script.sh

# на початку файлу - свідоме
# вимкнення правила:
# shellcheck disable=SC2086

    Вимкнути правило можна, але тільки рядком вище і з коментарем, чому. Глобально вимкнений SC2086 означає «ми вирішили не брати підстановки в лапки», і це рішення варто ухвалювати вголос.

    Для тестів є bats. Але перший тест будь-якого скрипту - запуск із --dry-run: режим, у якому він друкує, що зробив би, і нічого не робить. Його варто закласти одразу, а не після першого інциденту.

    Що запитують: «Чим ви перевіряєте shell-скрипти і що робить shellcheck такого, чого не бачить людина?»

    Артефакти: що у вас є після цієї сторінки #

    Скелет, який набирається не думаючи, і розуміння, чому саме такий. Час витрачено недаремно, якщо ви перестали пояснювати поломки словом «чомусь»: у кожної з них тут названо місце - режим оболонки, незакавичкована підстановка, втрачений код повернення або відсутня пастка. Це і є перебудова нейромережі: скелет ви забудете набрати з пам'яті через місяць, а причину, через яку він такий, - ні.

    1. Межа двох режимів: що читає інтерактивна оболонка, а що - скрипт.
    2. Скелет із п'яти рядків: shebang, суворий режим, IFS, usage, перевірка аргументів.
    3. Правило двох каналів: stdout - результат, stderr - все інше, код повернення - статус.
    4. Ідемпотентність і trap EXIT як вимога, а не як акуратність.
    5. shellcheck і --dry-run - дві перевірки, які дешевші за будь-який інцидент.
    Наступна сторінка - сила Bash: чому його досі не витіснили.
