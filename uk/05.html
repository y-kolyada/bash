    Взаємозв'язки

    Де Bash стикується з Git, CI, Docker, systemd, Make та Ansible - і що в кожному з цих швів ламається найчастіше.

    Головна думка сторінки #

    Bash рідко працює сам по собі: він живе всередині чужих інструментів, і більшість проблем виникає не в ньому, а на межі. Git-хук вирішує долю коміту кодом повернення. CI запускає ваш крок із власним набором ключів і новим процесом на кожен крок. Docker у рядковій формі ставить PID 1 оболонкою, і контейнер перестає зупинятися за сигналом. systemd розбирає ExecStart сам, без оболонки. Make та Ansible виконують кожен рядок у своїй оболонці. Вивчивши шість цих швів, ви закриваєте основну частину питань на асесменті - і більшу частину реальних інцидентів.

    1 · Git: хуки та фільтри #

    Git не має власної мови розширення - він запускає виконувані файли, і майже завжди це shell. Хук отримує дані через аргументи або stdin, а рішення ухвалює кодом повернення: ненульовий скасовує операцію.

    #!/usr/bin/env bash
# .git/hooks/pre-commit
set -euo pipefail

files=$(git diff --cached --name-only \
        --diff-filter=ACM | grep '\.sh$' || true)
[ -z "$files" ] && exit 0
shellcheck $files

    Дві пастки. Перша: grep без збігів повертає 1 і під set -e впустить хук - звідси || true. Друга: хуки не зберігаються в репозиторії, папка .git/hooks не версіонується; тому хуки кладуть в окремий каталог і вмикають через git config core.hooksPath, інакше в колег їх просто не буде.

    Що запитують: «Як змусити хук скасувати коміт і чому хуки не потрапляють до інших розробників самі?»

    2 · CI та GitHub Actions: shell за замовчуванням #

    Крок run: - це shell-скрипт, який CI пише в тимчасовий файл і запускає. Важливо знати, з якими ключами, і тут є тонкість, об яку спотикаються: якщо shell: не вказано, GitHub Actions запускає bash -e {0} - set -e є, pipefail немає. Якщо вказати shell: bash явно, запуск стає bash --noprofile --norc -eo pipefail {0} - pipefail з'являється. -u немає в жодному варіанті.

    - name: build
  shell: bash          # дає -eo pipefail
  run: |
    set -euo pipefail  # -u все одно свій
    ./build.sh

# кожен крок - новий процес:
# export в одному кроці не видно
# в наступному
echo "VER=1.2" >> "$GITHUB_ENV"

    Кожен крок - окремий процес, тому змінні між кроками передаються через файли ($GITHUB_ENV, $GITHUB_OUTPUT), а не через export. І окрема обережність: set -x у кроці друкує значення змінних, тобто виводить секрети в журнал - маскування рятує не завжди.

    Що запитують: «З якими ключами CI запускає ваш run: і як передати значення між кроками?»

    3 · Docker: PID 1, сигнали та форма запису #

    Найчастіша помилка в ENTRYPOINT не про shell, а про процеси. У рядковій формі команда запускається через /bin/sh -c, і PID 1 отримує оболонка, а не ваш застосунок - сигнал SIGTERM до нього не дійде, і зупинка контейнера перетвориться на вбивство за таймаутом.

    # погано: PID 1 - це sh
ENTRYPOINT /app/run.sh

# добре: exec-форма
ENTRYPOINT ["/app/run.sh"]

# і в самому скрипті, наприкінці:
exec /app/server "$@"

    exec замінює процес оболонки процесом застосунку - PID 1 стає застосунком, сигнали доходять. У контейнері немає init, тому зомбі-процеси ніхто не збирає; якщо ваш скрипт породжує фонові завдання, потрібен --init або tini. І пам'ятайте про Alpine: там /bin/sh - це busybox ash, і bash відсутній зовсім.

    Що запитують: «Чому контейнер не зупиняється за docker stop і до чого тут форма запису ENTRYPOINT?»

    4 · systemd: коли скрипт не потрібен #

    systemd вміє багато з того, заради чого пишуть скрипти-обгортки: перезапуск, залежності, обмеження ресурсів, журнал. Обгортка, яка лише запускає та перезапускає, зайва.

    [Service]
ExecStart=/usr/bin/app --port 8080
Restart=on-failure
EnvironmentFile=/etc/app.env

# ExecStart - не shell:
# ані $VAR, ані | , ані > тут немає
ExecStart=/bin/bash -c 'app | tee -a log'
# так - лише якщо без цього ніяк

    Рядок ExecStart розбирається самим systemd, а не оболонкою: підстановки, конвеєри та перенаправлення там не працюють. Якщо вони дійсно потрібні - виклик bash -c явний і усвідомлений. Логи пишуться в stdout/stderr і потрапляють до journalctl; саморобна ротація файлів у скрипті - майже завжди зайва робота.

    Що запитують: «Чому в ExecStart не працює перенаправлення і коли потрібен bash -c?»

    5 · Make та Ansible: кожен рядок - своя оболонка #

    Спільна помилка обох інструментів: рядки не продовжують один одного. У Make кожен рядок рецепта виконується в окремій оболонці, тому cd з першого рядка у другому вже не діє.

    # не працює:
build:
	cd src
	make all

# працює:
build:
	cd src && make all

# або один shell на весь рецепт:
.ONESHELL:

    В Ansible те саме: модуль shell запускає рядок заново для кожного завдання. І там ще одна відмінність, про яку запитують: command запускає програму напряму, без оболонки - без конвеєрів, підстановок і шаблонів імен; shell - через оболонку, з усіма можливостями та всіма ризиками. Правило: command, поки не доведено, що потрібен shell.

    Що запитують: «Чому cd у Makefile не діє на наступний рядок і чим command відрізняється від shell в Ansible?»

    6 · Де Bash закінчується: jq, awk, Python #

    Сусіди по екосистемі ділять роботу за типом даних, і знання межі економить години.

    # структура - jq
jq -r '.items[] | select(.ok).id' f.json

# колонки та арифметика - awk
awk -F, '{s+=$3} END{print s/NR}' f.csv

# все інше - мова
python3 -c 'import json, sys; ...'

    jq - для всього, що має вкладеність. awk - для порядкових даних із колонками та підрахунками; він же часто замінює зв'язку grep | cut | sort однією командою та одним процесом. Python - коли потрібні бібліотеки, мережа складніша за curl, або стан між кроками.

    Практична ознака: щойно в скрипті з'явився другий jq із власним виразом на три рядки - завдання вже не про Bash.

    Що запитують: «Коли ви берете awk замість зв'язки grep | cut і коли йдете в Python?»

    Артефакти: що у вас є після цієї сторінки #

    Карта швів замість набору рецептів. Час витрачено недаремно, якщо ви тепер запитуєте про чужий інструмент правильне: хто тут запускає мій рядок, у якому процесі та що він зробить із кодом повернення. Це і є перебудова нейромережі: питання «чому не працює» замінюється питанням «хто це виконує».

    1. Git: рішення - кодом повернення; хуки не версіонуються без core.hooksPath.
    2. CI: без shell: - bash -e, з shell: bash - ще й pipefail; -u немає ніде; змінні між кроками - через файли.
    3. Docker: exec-форма, exec наприкінці скрипту, відсутність init.
    4. systemd: ExecStart - не оболонка; логи в журнал, а не у файл.
    5. Make та Ansible: кожен рядок у своїй оболонці; command проти shell.
    6. Межа з jq, awk та Python за типом даних, а не за звичкою.
