    Практики у Clouds

    Слів: 1026

    CLI хмари, очікування готовності, доступи без ключів, ліміти API, захист від чужого акаунту та прибирання за тегами - і де проходить межа з Terraform.

    Головна думка сторінки #

    У хмарі Bash керує викликами чужого API, де кожен запит коштує часу, квоти та грошей. Якість хмарного скрипту визначають чотири правила: він чекає на готовність асинхронних ресурсів явно і з межею спроб; ніколи не зберігає ключі в коді й не світить їх під set -x; запитує дані пачками з урахуванням пагінації та лімітів API замість сотень викликів у циклі; і на першому ж рядку перевіряє, у який акаунт і регіон він дивиться. Все, що скрипт створив для завдання, він зобов'язаний уміти знайти та видалити за тегом. А архітектурна межа проста: одноразова дія - це Bash, постійний стан інфраструктури - це Terraform. Тріаж самої живої машини та її логів винесено в окремий розділ практик SRE.

    1 · CLI хмари - звичайна програма, і поводиться як програма #

    Перше, що змінює ставлення до хмарного CLI: це не консоль адміністратора, а утиліта з кодом повернення та машинним виводом. Отже, до неї застосовні ті самі правила, що й до grep.

    aws ec2 describe-instances \
  --filters Name=tag:app,Values=web \
  --query 'Reservations[].Instances[].InstanceId' \
  --output text

aws s3api head-object … >/dev/null 2>&1 \
  && echo є || echo немає

    Два прийоми економлять найбільше часу. --query фільтрує на боці CLI, до того як дані дійдуть до jq: менше тексту, менше розбору. Відсутність об'єкта - це ненульовий код повернення, а не порожній рядок; перевіряти треба код, а не вивід. І вимикайте вбудований пейджер через AWS_PAGER="", щоб скрипт не завис в очікуванні клавіші q.

    Що запитують: «Чим --query відрізняється від jq і як у скрипті перевірити, чи існує ресурс?»

    2 · Створення ресурсів: очікування - частина роботи #

    Хмарні виклики асинхронні: команда повернула ідентифікатор - це не означає, що ресурс готовий. Скрипт, який не чекає, падає через раз і виглядає як «плаваюча помилка».

    id=$(aws ec2 run-instances … \
     --query 'Instances[0].InstanceId' \
     --output text)

aws ec2 wait instance-running \
  --instance-ids "$id"

# власне очікування - з межею
for i in {1..30}; do
  ready && break
  sleep 5
done

    У CLI є вбудовані очікування (wait) - беріть їх. Там, де їх немає, пишіть цикл з обов'язковою межею спроб: нескінченне очікування в CI означає, що завдання висить до таймауту і витрачає хвилини. І позначайте все, що створюєте, тегами - за ними ви потім це знайдете і видалите.

    Що запитують: «Як у скрипті дочекатися готовності хмарного ресурсу і що буде без очікування?»

    3 · Доступи: чого в скрипті бути не повинно #

    Найдорожча помилка в хмарних скриптах не технічна, а дисциплінарна - ключ, що потрапив у репозиторій або в журнал.

    # ні:
AWS_SECRET_ACCESS_KEY=AKIA…

# так: роль інстансу або профіль
aws --profile prod s3 ls

# секрет - зі сховища, у змінну,
# і ніколи в echo і не під set -x
token=$(aws secretsmanager \
  get-secret-value --secret-id t \
  --query SecretString --output text)

    Порядок переваги: роль інстансу або OIDC - нічого зберігати не потрібно; профіль - ключі лежать у користувача, а не в коді; змінні оточення - лише як останній засіб. Окремо: set -x друкує значення, тобто виводить секрет у журнал CI; вмикати трасування в кроці, який працює з секретами, не можна.

    Що запитують: «Як скрипт отримує доступ до хмари без зберігання ключів і чому set -x там небезпечний?»

    4 · Пагінація, тротлінг API та заборона на виклики в циклі #

    Виклик хмарного CLI в циклі for за сотнею ресурсів - надійний спосіб упертися в ThrottlingException (Rate exceeded) і розтягнути скрипт на пів години: кожен виклик підіймає Python/Go-рантайм і відкриває нову TLS-сесію.

    # ні: N викликів API в циклі
for id in $ids; do
  aws ec2 describe-instances --instance-ids "$id"
done

# так: один пакетний запит і адаптивний retry
export AWS_RETRY_MODE=adaptive
export AWS_MAX_ATTEMPTS=6
aws ec2 describe-instances \
  --instance-ids $ids

    Два правила для великих хмар: передавати ідентифікатори пачкою або фільтром на боці API замість поштучного перебору, і вмикати вбудований адаптивний режим повторів (AWS_RETRY_MODE=adaptive), який сам знижує частоту запитів при відповіді 429/503. А при читанні великих списків пам'ятати, що без автопагінації або --next-token повернеться лише перша сторінка.

    Що запитують: «Чому хмарний скрипт раптово падає з помилкою Rate Exceeded і як позбутися викликів CLI в циклі?»

    5 · Захист від не того акаунту, регіону та контексту #

    Найбільш руйнівна аварія в хмарі стається, коли правильний скрипт очищення запускають у терміналі, де з учорашнього дня залишився профіль або контекст продакшену.

    #!/usr/bin/env bash
set -euo pipefail

export AWS_PAGER=""
region="${AWS_REGION:?вкажіть регіон}"
want_acc="123456789012"

got_acc=$(aws sts get-caller-identity \
  --query Account --output text)
[ "$got_acc" = "$want_acc" ] || {
  echo "чужий акаунт: $got_acc" >&2
  exit 1
}

    Будь-який скрипт, який змінює або видаляє хмарні ресурси, зобов'язаний у перших рядках звірити фактичний акаунт і кластер з очікуваним (aws sts get-caller-identity, gcloud config get-value project, kubectl config current-context) і вимагати явного зазначення регіону, не покладаючись на змінні, випадково успадковані з інтерактивної оболонки інженера.

    Що запитують: «Як гарантувати, що скрипт для тестової хмари випадково не видалить ресурси в продакшені?»

    6 · Прибирання та межа з Terraform #

    Хмара бере гроші за забуте. Скрипт, який створює, зобов'язаний уміти видаляти - і знаходити те, що потрібно видалити, за тегами, а не за списком у голові.

    aws ec2 describe-instances \
  --filters Name=tag:tmp,Values=yes \
  --query '…[].InstanceId' --output text \
  | xargs -r aws ec2 terminate-instances \
      --instance-ids

    xargs -r не запустить команду на порожньому вводі - без нього видалення «всього» може перетворитися на команду без аргументів із непередбачуваною поведінкою.

    Де проходить межа. Bash хороший там, де завдання про дію: створити на годину, зібрати зріз за акаунтом, мігрувати бакет, видалити за тегом. Terraform та CloudFormation - там, де завдання про стан: що має існувати постійно. Скрипт, який намагається підтримувати стан, неминуче перетворюється на поганий Terraform - зі своїм файлом стану, своєю перевіркою розходжень і своїми помилками.

    Що запитують: «Де закінчується скрипт провіжинінгу і починається Terraform?»

    Артефакти: що у вас є після цієї сторінки #

    Перевірка акаунту на вході та прибирання за тегом на виході. Час витрачено недаремно, якщо ви перестали викликати хмарний CLI в циклі по одному ресурсу і починаєте кожен скрипт зі звірки ідентифікатора акаунту, а створення кожного тимчасового ресурсу - з тегу. Це і є перебудова нейромережі: хмара перестає бути місцем випадкових рахунків і чужих регіонів.

    1. CLI як програма: код повернення, --query на боці клієнта, вимкнення AWS_PAGER.
    2. Явне очікування готовності через wait або цикл із межею спроб.
    3. Порядок доступів: роль або OIDC → профіль → змінна; заборона на set -x із секретами.
    4. Пакетні запити та AWS_RETRY_MODE=adaptive замість викликів CLI в циклі.
    5. Перевірка акаунту та регіону в першому рядку скрипту до будь-яких змін.
    6. Прибирання за тегами, xargs -r і межа: дія - Bash, стан - Terraform.
