    Практики DevOps

    Bash у конвеєрі постачання: збірка, середовища, деплой та відкат, перевірки до злиття та робота з секретами. І ознаки, за якими видно, що конвеєр переріс скрипт.

    Головна думка сторінки #

    У конвеєрі постачання Bash зустрічається найчастіше і помилки там найдорожчі, тому що крок CI - це ваш скрипт, запущений чужим способом: із чужими ключами, у новому процесі та в скинутому каталозі. Звідси перше правило - крок має бути самодостатнім, а довга логіка жити у файлі репозиторію, який можна запустити локально. Друге правило про збірку: версія береться із системи контролю, а latest версією не є, тому що за ним не можна відкотитися. Третє - один скрипт на всі середовища з обов'язковим аргументом, тому що замовчування рано чи пізно задеплоїть у прод. І четверте, про яке найчастіше запитують на співбесідах: відкат проектують раніше за деплой.

    1 · Bash у конвеєрі: чий це процес #

    Крок CI - це ваш скрипт, запущений чужим способом. Три факти про цей запуск визначають майже всю поведінку.

    # 1. ключі задає CI, не ви
#    без shell: -> bash -e
#    shell: bash -> + pipefail
set -euo pipefail   # -u - тільки свій

# 2. кожен крок - новий процес
echo "VER=$v" >> "$GITHUB_ENV"

# 3. робочий каталог скидається
cd "$GITHUB_WORKSPACE"

    Звідси правило: крок має бути самодостатнім. Він не покладається на export із попереднього кроку, не розраховує на поточний каталог і оголошує свій суворий режим сам. Довгу логіку виносять у файл .sh у репозиторії: його можна запустити локально, перевірити shellcheck і прочитати в diff - на відміну від двадцяти рядків усередині YAML.

    Що запитують: «Чому змінна з одного кроку CI не видна в наступному і як її передати?»

    2 · Збірка: відтворюваність важливіша за швидкість #

    Скрипт збірки відповідає на одне питання: чи вийде завтра те саме, що сьогодні. Все інше вторинне.

    ver=$(git describe --tags --always --dirty)
sha=$(git rev-parse --short HEAD)

docker build \
  --build-arg VER="$ver" \
  -t "app:$sha" .

# артефакт називається версією,
# а не latest

    Три правила, які ловлять більшість проблем. Версія береться із системи контролю, а не зі змінної - її не можна забути оновити. latest не є версією: за ним неможливо відкотитися. Суфікс --dirty показує, що зібрано з незакоміченого дерева - це той випадок, коли артефакт відтворити вже не можна, і про це краще знати одразу.

    Що запитують: «Звідки береться номер версії артефакту і чому не можна деплоїти latest?»

    3 · Середовища Dev → QA → Prod: один скрипт, різні параметри #

    Типова помилка - три схожі скрипти по одному на середовище. Через місяць вони розходяться, і деплой у прод робить не те, що перевіряли на QA.

    #!/usr/bin/env bash
set -euo pipefail
env="${1:?dev|qa|prod}"
cfg="deploy/$env.env"
[ -f "$cfg" ] || { echo "немає $cfg" >&2; exit 2; }
# shellcheck source=/dev/null
source "$cfg"

[ "$env" = prod ] && : "${APPROVED:?потрібне підтвердження}"

    Один скрипт, конфігурація зовні, середовище - обов'язковий аргумент. Жодних значень за замовчуванням для середовища: скрипт, який без аргументу деплоїть у прод, рано чи пізно задеплоїть у прод. Додатковий гейт для продакшену робиться явною змінною, а не коментарем на початку файлу.

    Що запитують: «Як один скрипт обслуговує три середовища і як ви захищаєте прод від випадкового запуску?»

    4 · Деплой та відкат: відкат проектують першим #

    Питання, яке ставлять на співбесіді частіше, ніж про сам деплой: як ви повернетеся назад. Якщо відповідь вимагає нової збірки - відповідь погана.

    # релізи поруч, поточний - посилання
ln -sfn "/opt/app/rel/$ver" /opt/app/next
mv -T /opt/app/next /opt/app/current
systemctl reload app

# відкат = той самий крок із минулою версією

    ln -sfn плюс mv -T дають атомарну заміну: у будь-який момент часу посилання вказує або на старий реліз, або на новий, проміжного стану немає. Простий запис rm symlink && ln -s такої властивості не має - між двома командами посилання не існує зовсім.

    Перевірка після деплою - теж частина скрипту: звернення до /health з межею спроб та автоматичне повернення на минулу версію, якщо відповіді немає.

    Що запитують: «Як зробити перемикання версії атомарним і як влаштований відкат?»

    5 · Якість конвеєра: перевірки до злиття #

    Перевірка скриптів - такий самий крок CI, як тести застосунку. Коштує він секунди, а ловить те, що інакше знайдеться в продіві.

    - run: |
    shopt -s globstar
    shellcheck **/*.sh
- run: shfmt -d -i 2 .
- run: bats tests/

    Той самий набір ставлять локально через pre-commit, щоб червоне не доїжджало до CI. Важливо, щоб локальна перевірка та перевірка в CI були однією і тією самою командою - інакше з'являється клас помилок «у мене проходить, в CI падає», і довіра до перевірки втрачається.

    Що запитують: «Які перевірки shell-коду ви ставите в конвеєр і чому вони мають збігатися з локальними?»

    6 · Секрети та журнали #

    Журнал CI - публічний для всіх, у кого є доступ до репозиторію, і він зберігається довше, ніж пам'ятають про секрет.

    # ні:
set -x               # надрукує все
echo "token=$TOKEN"
curl -u "u:$PASS" …  # видно в ps

# так:
curl --netrc-file "$f" …
printf '%s' "$TOKEN" | cmd --token-stdin

    Три правила. Секрет не передається аргументом - аргументи видно в ps усім користувачам машини; його передають через stdin, файл або змінну оточення. Трасування не вмикається в кроках із секретами. Маскування CI - не гарантія: воно підміняє точний збіг, і секрет, що потрапив у журнал частинами або в іншому кодуванні, у маску не потрапить.

    Що запитують: «Чому не можна передавати пароль аргументом команди і що робить маскування секретів у CI?»

    7 · Коли конвеєр переріс скрипт #

    Ознаки, що логіку час виносити з shell:

    • у скрипті з'явився стан, який треба пам'ятати між запусками;
    • кроки залежать один від одного нелінійно - це завдання для Make або графа CI, а не для послідовності;
    • одна й та сама логіка скопійована в три конвеєри;
    • для розуміння скрипту потрібно знати, які змінні виставляє CI.

    Перше лікується інструментом стану, друге - графом залежностей, третє - спільним скриптом у репозиторії або власною дією CI, четверте - перенесенням логіки у файл, який запускається локально тими самими командами.

    І зворотне: конвеєр із п'ятнадцяти рядків на Bash, який роблять зрозумілим три коментарі, не потрібно перетворювати на плагін. Складність інструменту виправдовується розміром завдання, а не його важливістю.

    Артефакти: що у вас є після цієї сторінки #

    Читання >> Ваш квант часу життя · Партнерство гідності разом з AI · Перебудова вашої нейромережі

    Розуміння, що крок CI - це чужий запуск вашого коду. Час витрачено недаремно, якщо ви перестали дивуватися тому, що в CI поводиться інакше, і почали запитувати: з якими ключами запущено, в якому процесі, що з робочим каталогом. Це і є перебудова нейромережі: конвеєр перестає бути чорною скринькою і стає місцем, де виконуються ваші ж команди.

    1. Три факти про крок CI: чужі ключі, новий процес, скинутий каталог.
    2. Версія з Git і заборона на latest у деплої.
    3. Один скрипт на три середовища з обов'язковим аргументом і гейтом для проду.
    4. Атомарне перемикання через ln -sfn та mv -T, відкат тим самим кроком.
    5. Перевірки до злиття, що збігаються з локальними.
    6. Правила секретів: не аргументом, без трасування, маскування не гарантія.
    7. Ознаки, що конвеєр переріс скрипт, і чим кожна з них лікується.
    Наступна сторінка - практики SRE: триаж інциденту, логи, захист від навантаження та метрики.
